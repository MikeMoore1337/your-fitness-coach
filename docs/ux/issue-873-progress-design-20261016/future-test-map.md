Это план тестов после owner design approval. До approval он не добавляет обязательные CI
checks и не меняет текущие тесты.

| Навигация | При программном переходе выбранная вкладка становится видимой и получает фокус без layout jump | активная вкладка за пределами scroll-контейнера |

## Playwright / browser evidence

Один параметризованный набор на synthetic API fixture должен пройти в Chromium и отдельно в
Mobile WebKit после реализации:

1. Размеры `320`, `360`, `393`, `430`, затем `1440`; светлая и тёмная темы.
2. У каждого раздела проверяются отсутствие горизонтального overflow, корректный selected
   tab, URL/deep link и браузерный Back.
3. `Тело`: bounding box CTA не меньше `44×44` CSS px; CTA виден в первом смысловом блоке,
   открывает существующую форму, validation и сохранение не изменились; edit/history доступны.
4. `Тренировки`, `Питание`, `Кардио`, `Самочувствие`, `История`: DOM assertions на числа,
   статусы missing/zero, раскрытие деталей, подтверждение удаления и две истории.
5. Keyboard: `Tab`, `Enter`, `Space`, `Home/End` для tablist; focus-visible не перекрывается
   dock; tooltip/help доступен без hover-only поведения и закрывается предсказуемо.
6. Safe-area/dock: скролл до CTA, последней строки, form submit и подтверждения удаления;
   `getBoundingClientRect()` не пересекается с нижним dock и visual viewport.
7. Визуальные captures: каждый impacted state минимум в light/dark; текущий `BEFORE` и
   предложенный `PROPOSED` сравниваются отдельно, без смешения с #1002 baseline.

## Ручные gates, которые автоматизация не заменяет

- Keyboard pass на реальном браузере с системным zoom.
- VoiceOver и rotor/heading/tab navigation: `NOT_VERIFIED` этим пакетом.
- Реальный iPhone/Safari и Telegram Mini App safe-area/dock: `NOT_VERIFIED` этим пакетом.
- Проверка owner-approved composition, затем real AFTER и owner visual acceptance.

## Неизменяемые ограничения

Не менять API, серверные расчёты, период, RBAC, privacy, существующую форму, validation,
`design-v2.css`, `progress-report-*` и общие snapshots в рамках макетной стадии. После #1002
любое затрагивание общих baseline интегрировать отдельным последовательным изменением.
