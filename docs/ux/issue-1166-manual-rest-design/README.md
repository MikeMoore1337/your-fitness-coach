## Почему это решение

На сопоставимых эскизах рассмотрены три расположения:

| Вариант | Структура                                            | Решение                                                           |
| ------- | ---------------------------------------------------- | ----------------------------------------------------------------- |
| A       | Sticky-строка → тренировка → текущий подход → dock   | Рекомендован: прежнее место панели, доступность при прокрутке     |
| B       | Тренировка → действие внутри текущего подхода → dock | Отклонён: действие уходит за экран и перемещается между подходами |
| C       | Тренировка → текущий подход → действие над dock      | Отклонён: конкурирует с клавиатурой и нижней навигацией           |

Эскизы реально отрендерены и просмотрены рядом. Нового направления дизайна нет: это EVOLVE
существующей панели, Oswald/Inter, текущих токенов, общей иконографии и YFC Dark/Light.
Три риска учтены: постоянная большая карточка мешала бы подходу — остаётся компактная строка;
отдельная плавающая кнопка спорила бы с dock — используется верхняя панель;
повтор метрик выглядел бы вторым таймером — ФАКТ принадлежит тому же интервалу.
Композиция привязана к рабочему подходу, плану/факту отдыха и его истории; универсальная
карточка управления без этого контекста не решает задачу.

## Подтверждённые ограничения текущего кода

- `TodayWorkout.tsx:1499–2020`: активный таймер сейчас скрыть нельзя; существующая кнопка
  `Скрыть` убирает terminal-уведомление. Измеряемый отдых после плана продолжает идти.
- `restSessions.ts:286–334`: автоматический start повторно использует running того же подхода,
  а после terminal возвращает `null`. Recovery, ACK и sync тоже ищут записи по `source_set_id`.
- `models/workout_rest.py:18`: `UNIQUE(source_set_id)` запрещает повторный интервал.
- `api/v1/workout_rest.py:110–114`: start возвращает старую строку независимо от статуса;
  `mutation_id` старта не сохраняется. Блокировка только исходного подхода не защищает
  от двух running-сессий разных подходов одной тренировки.
- `TodayWorkout.tsx:1593–1619`: rest-sync ошибки скрываются; баннер set queue не показывает
  реальное состояние сохранения отдыха.
- История, экспорт и статистика уже принимают список интервалов. Проверить повторные source set
  и сохранить семантику статистики интервалов, не превращая её молча в сумму на подход.

## План и зависимости после принятия макета

`контракт → миграция/API → журнал/offline/UI → регрессии → реальные AFTER → owner acceptance → выпуск`.
Интеграцию ведёт основной агент. Разные исполнители не редактируют один файл одновременно.

Минимальный предложенный контракт — прежний start endpoint с необязательной ссылкой на
предыдущий интервал (`restart_of_session_id`). Без неё сохраняется automatic start/replay
первоначального интервала, включая старых клиентов. В таблицу добавляются nullable
`start_mutation_id` и ссылка на predecessor; исторические ID, даты, статусы и замеры сохраняются.
Тот же mutation ID с тем же payload возвращает тот же результат; изменённый payload — 409.
Новый ручной запуск разрешён после terminal predecessor при валидном рабочем подходе и активной
тренировке; foreign ownership — 404, конфликт текущего состояния — 409, невалидные данные — 422.

Нужны уникальные start mutation и successor predecessor, а также сохранение единственного
первоначального интервала на source set. Блокировка workout перед start и единый порядок
блокировок в actions защищают новые старты в рамках одной тренировки. Уже существующие несколько
running нельзя автоматически завершать вымышленными датами: сначала read-only preflight.

Ключ локального интервала — существующий `start_mutation_id`, затем server ID. Старые journal v1
и recovery keys читаются без потери очереди. При offline sync сначала отправляются start/actions
predecessor, затем дочерний start; поздний ACK старого интервала не применяется к новому.
`source` сохраняет смысл достоверности (`USER_CONFIRMED` и т. п.), не признака ручного запуска.
Никаких изменений `is_completed`, веса, повторов, RIR или планового отдыха в программе.
Policy C остаётся прежней: 15 минут в фоне **и** 15 минут сверх плана требуют уточнения/исключения.

**Миграционный риск:** действующий `scripts/check_online_migrations.py` не разрешает снятие UNIQUE.
Нельзя пометить операцию как обычный expand или обойти gate. До реализации нужен узкий проверяемый
путь сохранения данных при ослаблении именно этого ограничения, с bounded lock/statement timeout
и регрессиями migration validator. Сначала добавить новые поля и защитные индексы, затем безопасно
заменить прежнее ограничение. Старый backend использует `.first()` по source set; rollback после
появления повторных записей требует проверки совместимости, удалять историю для rollback нельзя.
Проверка PostgreSQL и штатные capacity gates обязательны перед выпуском.

Точки изменения: `TodayWorkout.tsx`, `restSessions.ts`, ограниченный CSS `react.css`,
workout_rest model/schema/route, Alembic migration и штатный migration validator при необходимости,
unit/API/PostgreSQL/E2E тесты. `activeWorkoutQueue.ts` — только при доказанной необходимости.
Новый timer engine, система синхронизации, зависимости или контроллер доставки не нужны.
