# P1 · подтверждённый путь завершения подхода

P1_TYPE=INTERMITTENT. Воспроизведение: сборка `da5cfa89ebcb400bb7f0043cf6fd471d4fe2a353`, Chromium/WebKit.
Удержан ответ первого PATCH автосохранения веса. Пользователь вводит повторы и RIR и
нажимает завершение, пока существующий cross-context lock занят этим PATCH. Прежний
обработчик не ждёт асинхронный enqueue и отправляет fit:rest раньше принятия записи.
[BEFORE network/queue/server](p1-before.json): текущий set 201, сервер false, таймер 1.
Это доказанная причина рассинхронизации в воспроизведённом сценарии. Постоянная потеря
записи сервером и происхождение всех наблюдавшихся владельцем эпизодов не доказаны.

Исправление `7f78f0d7a28e9db0688fe763556b28ce9ba411a6`: enqueue возвращает boolean результата принятия. Online —
после flush с подтверждённым PATCH; offline — после успешного durable storage write.
Прежний completed useState удалён, источник completed — pending queue / server QueryCache.
Rest deadline сохраняется до fit:rest; переход на План во время pending PATCH не теряет
отдых. Повторные действия блокируются жизненным циклом операции, а не увеличением
600 ms debounce. Отдельный прежний debounce автосохранения полей не менялся.

При ошибке API queued данные остаются локально с явной надписью и состоянием «Требуется
действие», без ложного таймера; retry повторяет true, не превращается в undo. При отказе
storage offline операция не публикует completed state, текущий подход и ввод остаются.
Кадры ошибки сняты после прокрутки к существующей области синхронизации, чтобы сообщение
и действие повтора были видимы; обычная исходная/прокрученная геометрия проверена отдельно.
При одновременном отказе API и storage pending запись в памяти явно обозначена «Не
сохранено», без галочки; интерфейс предупреждает не закрывать приложение. Онлайн
memory fallback сохранён, но не выдаётся за долговременную запись.
Кардио использует тот же результат принятия и блокирует редактирование in-flight.
