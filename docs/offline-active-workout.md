# Офлайн-безопасная активная тренировка

Офлайн-режим ограничен уже начатой тренировкой. Приложение не пытается сделать весь продукт
доступным без сети и не выполняет фоновую синхронизацию после закрытия браузера. Service worker
из Task 86 нужен только для bounded static shell/assets и не дублирует canonical queue/snapshot
активной тренировки.

## Локальные данные

Для активной тренировки сохраняются только данные, необходимые для продолжения:

- минимальный снимок тренировки с упражнениями и подходами;
- введённые вес, повторы и отметка выполнения, а также выбранные необязательные параметры
  подхода: вид, повторы в запасе и достижение отказа;
- очередь ещё не подтверждённых сервером изменений;
- срок текущего таймера отдыха.

Детерминированная рекомендация прогрессии и её история сопоставимых сессий не нужны для продолжения
активной тренировки и перед сохранением снимка удаляются. Offline render не показывает устаревшую
рекомендацию до получения свежих server facts.

Ключи `localStorage` содержат `user_id` и `workout_id`. При logout, истечении auth-сессии или
явном входе в другой аккаунт данные предыдущего аккаунта удаляются. При завершении тренировки
удаляются её снимок, очередь и таймер. Повреждённый или несовместимый объект storage не
используется и удаляется.

Auth lifecycle использует общий sensitive-storage registry, поэтому вместе с active workout
очищаются другие пользовательские черновики, но сохраняется глобальная настройка темы. Полный
контракт описан во внутреннем `docs/private/account-data-export-and-browser-storage.md`.

Прежние ключи `fit_workout_set_*` и `fit_workout_pending_*` не имеют account scope. При первом
открытии начатой тренировки они переносятся только для входящих в неё server-confirmed set ID,
после чего удаляются. При logout или смене аккаунта оставшиеся legacy-ключи также удаляются.

Снимок активной тренировки позволяет восстановить экран после refresh или повторного открытия
Telegram Mini App без сети. Любое изменение подхода сразу попадает в локальную очередь. При
возврате сети, фокусе окна, восстановлении видимости или событии другой вкладки очередь
отправляется снова. `enqueue`, подтверждение операции, rebase после конфликта, сохранение snapshot
и очистка выполняются под одним per-workout cross-context lock. В браузерах с Web Locks
используется native lock; без него — versioned owner/ticket mutex в `localStorage`. Поэтому две
вкладки не могут перезаписать общий queue результатом stale read. Серверная идемпотентность
остаётся обязательной второй границей защиты.

Формат queue/snapshot остаётся `schema_version: 1` и ключи `fit_active_workout_v1_*` не меняются:
существующие данные читаются без преобразования. Отдельные служебные lock-records имеют собственный
prefix/version, не входят в workout payload и автоматически очищаются после release или истечения
lease. Миграция прежних unscoped draft-ключей остаётся идемпотентной.

Offline-shell открывается только когда в текущем `sessionStorage` уже есть access token и ID
аккаунта, ранее подтверждённый ответом `/api/v1/me`, а локальный snapshot принадлежит тому же ID.
Это позволяет пережить refresh и повторное открытие сохраняющего webview, но не создаёт локальную
auth-систему. Если Telegram WebView уничтожил session storage, приложение ждёт обычной server-side
проверки `initData` и не показывает private snapshot как авторизованный экран.

## API и версии

`PATCH /api/v1/workouts/sets/{set_id}` сохраняет обратную совместимость. Обычный запрос может
передавать только изменяемые поля. Офлайн-безопасный запрос дополнительно обязан передать пару:

- `expected_version` — версия подхода, на которой основано изменение;
- `mutation_id` — стабильный идентификатор одной локальной операции.

Поля передаются только вместе. Каждый успешный PATCH увеличивает `version` подхода. Операции с
`mutation_id` записываются в `workout_set_mutations` вместе с fingerprint полезной нагрузки.
Повтор той же операции возвращает текущее состояние подхода и не применяет изменение второй раз,
в том числе если первоначальный HTTP-ответ потерялся или тренировка уже завершена. Повторное
использование идентификатора с другой нагрузкой возвращает `409`.

## Конфликты и две вкладки

Если `expected_version` устарела, backend возвращает `409` с кодом
`workout_set_version_conflict` и текущим состоянием подхода. Клиент обновляет базовую версию и
повторяет локальное изменение. Если в общей очереди уже есть более новое изменение того же
подхода, устаревшая операция удаляется, а повторяется только последнее пользовательское значение.
Это не позволяет запоздавшему запросу из второй вкладки перезаписать более новый ввод.

Если тренировка больше не активна, backend возвращает `workout_not_active`. Клиент не пытается
открыть или изменить завершённую тренировку, не очищает неподтверждённые данные молча и показывает
контролируемый конфликт. Завершить тренировку из текущей вкладки можно только после успешной
синхронизации всей очереди.

`POST /api/v1/workouts/{workout_id}/finish` идемпотентен для уже завершённой тренировки текущего
владельца: повтор возвращает `200` и актуальное completed-представление без повторного изменения
timestamps, progression или других terminal side effects. Это восстанавливает сценарий, когда
первый успешный HTTP-ответ потерялся. И первый успех, и такой retry заставляют frontend
инвалидировать workout queries, принять completed-представление и под per-workout lock удалить
queue, snapshot и rest timer. Ownership, проверка состояния до первого завершения, подтверждение
незаполненных подходов и server-side scheduled-day rules остаются обязательными.

Завершённое представление содержит детерминированный `completion_summary`. В день выполнения его
можно повторно получить через `GET /api/v1/workouts/today`, даже если завершение сделало программу
неактивной. Необязательная субъективная оценка и заметка сохраняются отдельным идемпотентным `PUT`,
но не входят в offline queue подходов: при ошибке форма сохраняет введённый текст в текущем UI и
позволяет повторить отправку после восстановления сети. Полный контракт описан в
`docs/workout-completion-summary.md`.

Ownership по-прежнему определяется связью `user_workout_sets -> user_workouts -> user_programs`
и текущей server-side auth-сессией. `user_id` из localStorage никогда не используется как
авторизация API-запроса.
