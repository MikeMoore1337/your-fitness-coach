# История ориентиров КБЖУ

## Канонический контракт

Каждая версия суточных ориентиров калорий, белков, жиров и углеводов хранится в
`nutrition_targets`. Период версии полуоткрытый: `[effective_from, effective_to)`. Поэтому цель
действует в `effective_from`, но уже не действует в `effective_to`.

Для пользователя существует не больше одной открытой версии (`effective_to IS NULL`). Сохранение
новой цели блокирует строку пользователя в транзакции, закрывает текущую версию и связывает её с
новой через `superseded_by_id`. Одинаковый повтор запроса в ту же дату возвращает уже созданную
версию. Изменение значений в ту же дату сохраняет предыдущую запись как версию нулевой длительности:
она остаётся в аудиторской истории, но не действует ни в один календарный день.

Разрешённые источники:

- `calculated` — подтверждённый результат калькулятора пользователя;
- `manual` — значения, введённые пользователем без пересчёта;
- `trainer` — назначение действующего тренера своему клиенту;
- `adaptive` — явно принятое пользователем предложение адаптивной калибровки.

`created_by_user_id` реализован существующим FK `assigned_by_user_id`, а `created_at` — существующим
локальным timestamp `saved_at`. API возвращает канонические и совместимые legacy-поля из одного
источника, без дублирования значений в БД.

## Даты, история и конфликт изменений

Дата начала интерпретируется в IANA-часовом поясе владельца цели. Базовую цель можно изменить только
на текущую дату; будущая дата и новые изменения задним числом запрещены. Идентичный повтор уже
сохранённого запроса возвращает существующую версию, даже если календарный день сменился. Источник
и автор изменения видимы пользователю.

При завершении дня сохраняется ссылка на действовавшую версию цели или отметка об отсутствии цели.
Позднее изменение базовой цели не меняет этот день, в том числе если статус дневника затем сброшен.
Для дня, завершённого до появления снимков, ссылка создаётся перед изменением цели в тот же день.
Миграция не выдумывает цели для существующих дней и не изменяет старые записи.

Ручная цель на одну дату сохраняет значения в `nutrition_targets`, а запись
`nutrition_target_date_overrides` связывает их с датой и автором. Для выбранной даты последняя
запись имеет приоритет над базовой целью; снимок завершённого дня имеет приоритет над обеими.
Другие даты не меняются. На прошедшую дату и для уже завершённого дня новое назначение запрещено.
`POST /api/v1/nutrition/targets/dates` требует `Idempotency-Key`: точный повтор возвращает прежний
результат, повтор с другим содержимым отклоняется. `GET` по тому же пути показывает историю
назначений; доступ тренера проверяется при каждом запросе.

`GET /api/v1/nutrition/targets/program-day` читает тип календарного дня и тип недели из указанной
версии программы без создания тренировок. Для ротации без календарного расписания и дат за пределами
программы тип не определяется. Выполнение тренировки не используется для расчёта типа дня.

Правила расписания хранят ссылки на значения в `nutrition_targets`, а привязка хранит конкретную
версию программы. Приоритет: снимок завершённого дня, назначение на дату, правило будущих повторений,
уточнение типа недели, цель типа дня, базовая цель. Восстановление используется только после
явного назначения повторяющегося дня. Новые правила действуют с будущей даты; прошедшие правила
остаются в истории. Изменение программы само по себе не меняет привязку и будущие цели.

`GET /api/v1/nutrition/targets/schedule/binding` сообщает об изменении версии программы.
`POST .../binding/preview` показывает изменения для выбранного диапазона до 93 дней без записи;
другие диапазоны можно запросить отдельно. `POST .../binding/confirm` применяет новую версию только
при явном подтверждении и совпадении ожидаемой предыдущей привязки. Повторные запросы сохранения и
подтверждения используют `Idempotency-Key`; отозванный тренер не может их выполнить.

Существующая single-row цель мигрируется как `calculated` с `effective_from = DATE(saved_at)`. Более
ранняя история не выдумывается. Calculator context может быть `NULL` у первой ручной цели; точные
введённые КБЖУ при этом остаются полными и пригодными для дневника и отчётов.

## Миграции и восстановление

Миграции `0149`–`0152` добавляют снимки, назначения и правила без пересчёта существующих целей.
Перед отдельно разрешённым применением используйте действующие [порядок развёртывания](deployment.md)
и [план backup/restore](operations/v11-rec-01-off-host-backup-recovery.md): сохраните проверенную
копию схемы и данных с её Alembic revision, проверьте восстановление в разрешённом изолированном
контуре и применение миграций к восстановленной копии. Сверьте цели и завершённые дни до и после.
Восстановление production из копии требует отдельного разрешения и оценки записей после её создания.

На синтетической PostgreSQL проверены `pg_dump`/`pg_restore`, сохранение существующих целей при
`0149`–`0152` и отказ `0152` от потери явно заданного типа дня при downgrade. Это не проверка
production-копии. Штатный rollback приложения не делает Alembic downgrade: заполненные новые
данные защищены от удаления проверками миграций, поэтому при отказе сохраняйте схему и данные и
готовьте исправление вперёд.

## Ручная проверка энергии

Справочная энергия вычисляется детерминированно как `protein_g * 4 + fat_g * 9 + carbs_g * 4`.
Порог заметного расхождения — большее из `100 ккал` и `10%` указанной калорийности. Это product
heuristic для обнаружения вероятной ошибки ввода с запасом на округление и различия маркировки, а не
медицинская норма. При превышении порога пользователь должен явно подтвердить сохранение; backend
повторяет ту же проверку и хранит исходные значения без silent correction.

## Потребители и lifecycle

- Дневник и план выбирают цель на запрошенную дату, включая снимок завершённого дня.
- Progress/adherence выбирает версию по дате каждого заполненного дня; день без effective target не
  превращается в ноль и не входит в denominator соблюдения цели.
- Принятое adaptive proposal создаёт `source=adaptive`, а не изменяет строку на месте.
- Экспорт аккаунта сохраняет совместимое поле `nutrition` для текущей версии и полный список
  `nutrition_target_history`; снимки завершённых дней входят в `nutrition_target_day_snapshots`.
- Ручные назначения и их авторы входят в экспорт `nutrition_target_date_overrides`; их значения
  остаются в `nutrition_target_history` с признаком `target_scope=date`.
- Привязки и правила расписания входят в экспорт вместе с авторами; их значения хранятся в той же
  истории целей с признаком `target_scope=schedule`.
- Удаление аккаунта удаляет принадлежащую пользователю историю каскадно. При удалении автора у чужих
  версий author FK очищается, но сами значения и периоды клиента сохраняются.

Активный тренер может создавать и читать версии только для своего клиента. После прекращения связи
новые записи и доступ к trainer endpoint истории запрещены server-side; видимость controls во
frontend не является границей авторизации.
