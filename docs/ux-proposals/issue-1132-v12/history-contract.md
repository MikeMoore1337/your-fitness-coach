# #1132: контракт фактической истории подхода

Реализован `GET /api/v1/workouts/{workout_id}/set-history`. Это проекция существующих `UserProgram`, `UserWorkout`, `UserWorkoutExercise` и `UserWorkoutSet`, без нового хранилища истории, миграции или изменения прогрессии #917. Runtime UI ещё не использует этот endpoint.

## Два независимых факта

Для каждого существующего подхода ответ содержит `previous_today` и `previous_workout`.

- `previous_today`: предыдущий завершённый подход этого экземпляра упражнения в порядке исполнения (разминка перед рабочими). Незавершённые строки и плановые значения пропускаются. Для первого подхода — `null`.
- `previous_workout`: фактические `actual_weight`/`actual_reps`, ID и версия источника, `completed_at` и `performed_on`. Вес `0` сохраняется; отсутствие веса не заменяется плановым значением. Дата берётся из фактического завершения, не из `scheduled_date`.

`build_exercise_history` остаётся источником общей аналитики упражнения. Его `recent_sessions` объединяют факты по упражнению и фильтруют рабочий объём, поэтому не доказывают соответствие конкретному подходу. Старые exercise/workout history API сохраняют свои контракты; серверного previous-set endpoint до этой задачи не было, текущая подсказка вычисляется в `TodayWorkout.tsx`.

## Выбор и доказательство соответствия

1. Оба назначения принадлежат текущему пользователю. Разрешены текущее назначение и его явные `restarted_from_program_id` предки того же владельца. Другие назначения, даже с тем же упражнением, не подходят. Циклическая либо чужая lineage не открывает чужую историю.
2. Совпадают сохранённый canonical exercise FK, `source_template_exercise_id` и логический `day_number`. По названию, соседнему месту и null identity совпадения не угадываются. Перенос даты не меняет эту позицию. В циклах K=3,N=16 используются сохранённые позиции, а не номер календарной недели или живой шаблон.
3. Сначала выбирается последнее подходящее завершённое выполнение по фактическому времени. Только после этого ищется подход. Если №3 отсутствует, не завершён, лишён фактов либо не соответствует роли, возвращается `null`; более старое выполнение, №2 и №4 не используются.
4. Для сопоставления нужна сохранённая валидная структурная prescription. Совпадают вся последовательность ролей/позиций и группы, включая group position, rounds и exercise slots. Для внешней группы/суперсета совпадают также позиции и canonical ID участников. Разное число или порядок структурных сегментов означает недоказанное соответствие. Изменения только целей веса/повторов, отдыха или заметок не меняют идентичность.
5. Совпадают `set_number`, ненулевой `set_kind`, `planned_role`, `planned_position`, `planned_group_id`, `planned_group_kind`, `planned_round`. Строка должна соответствовать собственному сохранённому плану. Разминка, рабочий, top/back-off, drop, cluster, superset и circuit не подменяют друг друга.

Ограничения с отказом в сопоставлении:

- В текущей модели нет достоверной стороны выполнения. Для canonical unilateral/alternating упражнений и неизвестного каталога возвращается `identity_unproven`; левую и правую стороны по номеру не угадываем.
- Legacy/null позиции или отсутствующая структурная prescription также дают `identity_unproven`. План, сторону и lineage не восстанавливаем при чтении.
- Для порядка используется уже внедрённый в dev фактический `completed_at_utc` (#835). Если UTC отсутствует, локальное время рассматривается как диапазон ±24 часа, без подстановки нынешнего часового пояса. Время старта без UTC также остаётся диапазоном; для ещё не начатой тренировки граница — системное UTC-время. Источник допустим только если он доказанно раньше этой границы и позже остальных кандидатов: диапазоны не пересекаются. Для двух старых локальных отметок это требует разрыва более 48 часов. При неоднозначности или полностью отсутствующем времени подходящего завершённого выполнения — `identity_unproven`, без перехода к старой записи. Сохранённая локальная дата завершения не пересчитывается в нынешний часовой пояс и не выдаётся за UTC. Новая миграция или запись UTC при чтении не создаётся.
- У ещё не материализованного/устаревшего планового cycle workout история не подтверждается. Endpoint сам не запускает materialization.

Тип недели намеренно не вычисляется по текущему шаблону. Этот справочный API не предоставляет evidence для рекомендаций, не меняет правила #917 и не переносит значения в текущий ввод.

## Актуальность, права и отсутствие записей

Один рекурсивный SELECT читает lineage, текущие версии, идентичности и исторические факты в одном снимке PostgreSQL. Нет hydration, flush, commit, создания подходов или audit/history записей. RBAC проверяется в самом запросе, включая каждого предка. Чужому владельцу, тренеру и администратору без владения возвращается 404; без авторизации — 401. Ответ `private, no-store`.

Каждая строка привязана к `workout_id`, `workout_exercise_id`, `exercise_id`, `source_template_exercise_id`, `set_id`, `set_number`, `set_version`; сверху возвращаются назначение и его текущая ревизия. Статусы: `matched`, `no_previous_workout`, `no_matching_set`, `identity_unproven`. Последние три отображаются как «Нет прошлого результата», без соседнего веса или скрытого prefill.

После визуального утверждения клиент должен сравнивать эти привязки с текущим workout, отбрасывать опоздавший ответ после замены упражнения/ревизии/версии и получать историю после завершения существующего queue flush. При 409 нужны актуальные версии и повторное чтение; конфликт не даёт права перезаписать факт. Offline/reconnect и кэш ещё не интегрированы в runtime UI и остаются NOT_RUN. Незавершённый локальный ввод не становится «Предыдущим сегодня».

## Проверки

`backend/tests/test_workout_set_history.py` покрывает 1–4 и N=17, отсутствие/пробел №3 без старого fallback, отсутствие фактов, роли/виды, warmup/top/back-off/drop/cluster/superset/circuit, неизвестную сторону, порядок/состав, lineage и чужого владельца, частичное выполнение, настоящую API-выдачу K=3,N=16, restart, перенос и календарную границу, повторные чтения, API 409 и PostgreSQL commit во время SELECT. Последний тест проверяет единый снимок фактов и версий двумя настоящими транзакциями; SQLite его не подтверждает.
