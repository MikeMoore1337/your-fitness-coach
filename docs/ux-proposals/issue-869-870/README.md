# YFC - owner-review макеты #869 и #870, v1 (2026-10-12)

**Статус:** `OWNER_DESIGN_APPROVAL=PENDING`. Только визуальные **идеи локальных правок**, **не макеты целых экранов 1:1**. Нельзя заменять существующие экраны питания и профиля представленными SVG. Это не реализованный UI, не production, не разрешение на merge/deploy. Данные в изображениях синтетические.

**Roadmap:** #869 и #870 относятся к отдельному мобильному UI/UX-аудиту #859 и **НЕ входят в Product V11**. V11 посвящён техническим улучшениям и не должен включать визуальную переделку экранов.

## #869 - компактные вторичные действия питания
[Открыть Dark/Light SVG](./869-compact-mobile-v1.svg)

**Идея:** оставить дневник/добавление продуктов/КБЖУ в основном потоке, а «План питания» и «Список покупок» разместить внутри одной компактной группы «Планирование»: две строки одинакового приоритета, название и одно дополнительное пояснение, стрелка в конце. Никаких двух конкурирующих высоких карточек.

Что остаётся без изменений: текущая схема дневника, быстрый ввод, добавление воды, пищевые значения, база продуктов, списки покупок, маршруты, API, история и состояния кнопок гидратации `+250/+350/+500 мл`. Фактический порядок секций и положение группы относительно нижнего контента согласовать по реальному скриншоту на 320/360/393/430; SVG отражает иерархию, а не буквальные реальные пользовательские данные.

## #870 - профиль без дублей навигации и вложенной прокрутки
[Открыть Dark/Light SVG](./870-compact-mobile-v1.svg)

**Идея:** полная выбранная цель (2-3 строки) с отдельной видимой кнопкой изменения; ниже простая секция предпочтений без отдельного scroll-контейнера (прокручивается вся страница); ещё ниже компактный список существующих ссылок профиля вместо повторения крупных навигационных карточек. Никакие страницы, маршруты, настройки и предпочтения не удалять. Чекбоксы и названия упражнений в макете **условные примеры**, не предполагать конкретных пользовательских данных или реального API.

## До реализации
1. Представить эти макеты владельцу и получить выбор/правки.
2. При подтверждении внести макет, версию, SHA и допуски по адаптивности в Issues #869 и #870; утвердить только структуру, не выдуманные значения.
3. Реализовывать **исключительно локальные поправки в существующих реальных экранах**, предварительно показав BEFORE и *точечный* AFTER по затронутым блокам. **Не реализовывать цельный SVG 1:1** и не придумывать другие поля/данные/маршруты. Использовать существующие `Inter/Oswald`, дизайн-токены, Liquid Glass только в согласованной области, существующие selected/pressed/focus стили. На 320/360/393/430 учитывать реальные данные, переносы, safe area и непрерывную прокрутку.
4. Проверить доступность 44px, полное описание цели, отсутствие конфликтов вложенной прокрутки, сохранение всех prefs и маршрутов, Dark/Light, Chromium/WebKit/TMA, без изменения server-owned состояния.
5. Выгрузить **настоящие AFTER** из работающей сборки и сравнить с **утверждёнными владельцем локальными правками**, а не с этим иллюстративным полноэкранным SVG; запросить повторную визуальную приёмку.
6. До отдельного owner release approval не выполнять merge/deploy.

**Из SVG нельзя извлекать обязательные размеры всего экрана.** Возможная идея - компактные вторичные строки с зонами касания не менее 44px, переносы на 320px без горизонтального overflow. Расположение и размеры только по снимкам реального приложения и отдельному согласованию. Точные цветовые токены/типографика берутся из действующего `docs/design/YFC_PRODUCT_UI_CONTRACT.md` на этапе реализации, SVG содержит только близкие проектные значения.
