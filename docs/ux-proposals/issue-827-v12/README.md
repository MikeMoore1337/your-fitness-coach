## Три композиции и выбор

| Вариант                | Пространственная структура и основное действие                                                                                        | Решение                                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| A «Распределение»      | Все группы в общем списке; две полосы на группу; выбранная строка открывает источники справа на desktop и сразу под строкой на mobile | Рекомендуется: отвечает на «какие группы участвовали», сохраняет общую картину и связь с упражнениями |
| B «Сравнение периодов» | Главная область — ведомость двух равных периодов; текущие/предыдущие числа и две роли в отдельных строках                             | Не выбран: сравнение доступно не всегда, а таблица плотнее на 320px                                   |
| C «Профиль группы»     | Индекс групп перед большим профилем одной группы; выбор определяет всё содержимое основной области                                    | Не выбран: требует переключений, чтобы увидеть распределение целиком                                  |

Три wireframe отрисованы и просмотрены до выбора. В A сохранены фирменные чёрный/белый + лайм, Oswald/Inter и selected capsule из общего CSS. Функциональные glyphs скопированы из shared `iconGlyphs.tsx` для автономного прототипа; действуют существующие Lucide/Phosphor notices. Runtime будет использовать `Icon` и shared primitives напрямую.

Проверка на шаблонность: отдельные карточки на каждую мышцу заменены общей сопоставимой шкалой; декоративный силуэт исключён; цветовые «оценки тела» заменены двумя явно подписанными ролями. Общие счётчики нужны для интерпретации тренировочного журнала, не для декоративной dashboard-сводки. Замена логотипа на магазин или SaaS разрушила бы структуру: здесь нужны отношения подход → упражнение → роль мышцы и равные тренировочные периоды.

Верхняя оболочка автономного HTML задаёт контекст и не является разрешением менять весь «Прогресс». При реализации сохраняются текущие AppShell, управление периодом, остальные показатели, data-confidence, история упражнений и доступные разделы. Область изменения — существующий `MuscleWorkloadList` и её встраивание. Фактический BEFORE показывает детали текущего интерфейса, которые автономный макет сокращает.

## Фактические данные

[fixtures.json](fixtures.json) содержит 12 ответов, рассчитанных настоящим `services/analytics.py::build_training_analytics` и проверенных `TrainingAnalyticsResponse.model_validate`: четыре состояния × 7/30/90 дней. Генератор и дополнительные assertions повторно запущены основным агентом: PASS.

| Пример                 | 7 дней: подходы / тренировки | 30 дней | 90 дней |
| ---------------------- | ---------------------------- | ------- | ------- |
| Заполненный            | 36 / 3                       | 48 / 5  | 60 / 7  |
| Неполные связи         | 38 / 3                       | 50 / 5  | 62 / 7  |
| Пустой                 | 0 / 0                        | 0 / 0   | 0 / 0   |
| Все подходы без связей | 6 / 3                        | 6 / 3   | 6 / 3   |

Уникальные подходы берутся только из верхнего `completed_set_count`. Суммы групп не складываются. Пример Трицепса: всего 24, основное 8, вспомогательное 16, предыдущий период 6, изменение +18; это отдельные готовые поля ответа, не новый расчёт нагрузки. Частота берётся из ответа и относится к тренировкам, а не числу дней посещения.

`current=null` и `previous=null` явно сохраняются как отсутствие данных; отсутствующее сравнение не превращается в ноль. Общее предыдущее количество подходов в API отсутствует и в макете не показывается. Счётчик без muscle metadata означает отсутствие всех мышечных связей у упражнения; он не сертифицирует полноту каждой вспомогательной связи. Каталог описывает участие, а не измеряет воздействие. Нет recovery/fatigue/readiness/эффективных подходов или процентов эффективности.

Источник для реализации: `backend/fitminiapp_api/services/analytics.py:530`, `:572`, `:620`, `:675`, `:698`, `:781`; существующий потребитель `frontend/src/features/workouts/MuscleWorkload.tsx`, встраивание `ProgressExperience.tsx:898`. Новая система подсчёта и backend не нужны. В HTML JS выполняет только форматирование/выбор готовых snapshots и масштабирует длину графической полосы.
