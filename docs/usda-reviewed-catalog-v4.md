# USDA FoodData Central: закрытие #938 (версия v4)

## Данные

Один общий канонический каталог YFC, `source_name=usda-fdc-reviewed-ru`,
USDA CC0-1.0, без параллельных таблиц или внешних платных провайдеров.

- v2: 118 FNDDS ID.
- v3: ещё 97 FNDDS ID (215).
- v4: ещё 9 Foundation и 9 SR Legacy ID (233).
- Проверенное русское название привязано к точной тройке
  `fdcId + dataType + description`. При расхождении имя не присваивается,
  импорт отвергается.
- Нутриенты на 100 граммов валидируются: ккал, белки, жиры, углеводы и
  единицы. Клетчатка, если отсутствует, остаётся `null`.
- Для современной Foundation используются фактические значения энергии:
  сначала 1008, затем 2048 (Atwater specific), затем 2047 (Atwater general).
  Это именно атрибуты USDA, не вычисление YFC из БЖУ. Не переносить такое
  правило на SR Legacy/FNDDS и не конвертировать килоджоули как килокалории.
- Похожие продукты из разных исследований остаются разными по FDC ID,
  не объединяются только из-за одинакового русского названия.
- Русский поиск поддерживает точные группы; состояние сырой/приготовленный,
  наличие кожи и вид крупы нельзя схлопывать в результате.

## Строгая проверка перед выпуском

1. Получить полный проверенный набор через официальный USDA API
   (запросы ограниченными пакетами). **Нет ключа в репозитории или логах**.
2. Провалить импорт при неизвестном ID, другом `dataType`, изменённом
   `description`, пропуске обязательного нутриента или неверной единице.
3. `compare_usda_reviewed_catalogs.py` с предыдущим сохранённым снимком
   должен возвращать `added=18, removed=0, changed=0` перед первой
   публикацией v4. При отличии старых полей - обязательное ручное ревью.
4. Снять `pg_dump -Fc -t public.foods` до изменения базы и подтвердить
   `pg_restore --list`. Сохранить отдельную копию исходного JSON.
5. Импортировать исключительно через `import_food_catalog` с upsert по
   `(source_name, external_id)`; проверить `created=18`, затем
   повторную загрузку с `created=0`; не менять пользовательские записи.
6. Проверить живой RU поиск и статусы backend/worker/bot, публичный HTTP.

## Безопасная периодическая актуализация

Проверка проводится **ежеквартально** через `yfc-usda-audit.timer`
(`*-01,04,07,10-01 05:00:00 UTC`, с распределённой задержкой до 30 минут,
а также при старте после пропущенного срока). Она:

- запускает `scripts/run_usda_catalog_audit.sh` из **текущего проверенного
  релиза** YFC в backend-контейнере, использует существующие настройки прокси
  и ключ USDA из контейнера;
- получает новый snapshot официальных фиксированных ID, сравнивает с
  неизменяемым одобренным `usda_reviewed_approved.json`;
- сохраняет дату проверки, контрольные SHA256, итоговые числа, отдельный
  `candidate.json` и `report.json` в
  `/srv/yfc/backups/food_catalog/audits/<UTC-timestamp>/` (каталог 0700,
  файлы 0600);
- завершает `0` при идентичном наборе, `2` при отличии/новых данных
  (`needs_review`), `1` при недоступности или невалидном ответе USDA;
- **никогда не вызывает импорт и не обновляет согласованный снимок**.
  Изменённые данные остаются в очереди для review, а systemd фиксирует
  неуспешный запуск, если обнаружено изменение или ошибка;
- совместное выполнение блокируется `flock`; аудит не выводит ключ,
  данные пользователей или сырой ответ API в общий системный журнал;
- отдельная проверка внешнего источника не зависит от того, редактирует ли
  пользователь дневник: никаких записей в таблицы `Food`, `FoodDiary`
  и `NutritionTarget` не выполняется.

Команды оператора:

```sh
systemctl list-timers yfc-usda-audit.timer
systemctl start yfc-usda-audit.service
systemctl status yfc-usda-audit.service
journalctl -u yfc-usda-audit.service -n 40 --no-pager
find /srv/yfc/backups/food_catalog/audits -name report.json
```

При status `needs_review` оператор анализирует разницу, изменяет
проверенную карту ID/source и её версию в отдельном PR, повторяет тесты/CI,
получает согласование на изменение значений и только затем отдельно
производит data rollout с резервной копией. Неизменность исходного снимка
является обязательным условием автоматизации.

## Метрики приёмки

Зафиксировать реальную сумму `v3 -> v4`, количество записей по каждому типу,
изменения ранее опубликованных полей (должно быть ноль), идемпотентность,
работоспособность расписания, фактический результат пробного аудита и
статусы production. Приоритет - доказательство сохранности, а не обещание
абсолютного охвата USDA.
