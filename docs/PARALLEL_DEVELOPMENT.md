# Параллельная разработка YFC

Согласованная модель: до трёх одновременных независимых задач Codex Desktop. Каждый поток использует отдельный Git worktree, короткую ветку и собственный PR. GitHub Issue -> branch -> PR -> required Checks -> protected master -> Actions deploy/smoke остаётся единственным процессом доставки.

## Границы допуска

Новая задача может стартовать только из `Ready` и только внутри **явно разрешённого владельцем набора**. Подбор задач может быть автоматическим в пределах этого набора; система не переходит к следующей продуктовой версии и не пополняет список по собственной инициативе. Если совместимых задач меньше трёх, оставшиеся потоки свободны.

Перед запуском проверить по текущему GitHub:
1. DoR, номер родительского Epic и допуск продуктовой версии.
2. `Blocked by` / `Blocking` и отдельные owner-gates.
3. Открытые PR и ветки, не начата ли реализация той же Issue.
4. Прямые и косвенные пересечения: изменяемые файлы, миграции Alembic, общие схемы БД, API, TypeScript-контракты, конкурентные изменения shared components.
5. Нет ли уникальной незакоммиченной работы в worktree, которую нельзя трогать.

## Совместимость

- Независимые: можно параллельно.
- Потенциально конфликтующие: нужен явный контракт и совместимые изменения, иначе последовательно.
- Зависимые: последовательно после снятия блокера.

Отсутствие общих путей в Git **не доказывает** независимость контрактов. Совпадение файлов **не всегда** запрещает работу, но требует явной оценки.

## Интеграция

- Разработка/тестирование параллельны, интеграция в `master` последовательно по утверждённому GitHub Flow.
- Перед merge required Checks должны относиться к актуальному PR head и текущему master; несовместимые изменения требуют обновления ветки и повторных тестов.
- Одна задача - один ответственный PR. Дополнительные агенты внутри задачи не становятся независимыми владельцами Issue.
- Завершение Codex и зелёный CI не означают `Done`. Release Check/Owner Approval сохраняются.
- Визуальный redesign, правовые и рискованные изменения требуют владельца до соответствующего действия.
- Production deploy - через существующие Actions, без параллельной записи или обхода защиты. Проверить поведение `concurrency.group: production` и доставку последнего SHA при серии merge до включения расширенной автоматизации.
- Не создавать новый controller, lease, queue, lifecycle orchestration или БД. Если нативных возможностей недостаточно, `NEW_ORCHESTRATION_OWNER_APPROVAL_REQUIRED`.

## Пилот и измерения

Первая проверка - оценить три действительно независимые существующие Issue/PR (read-only), затем локальные worktrees с целевыми тестами. Измерять успешность CI, конфликты интеграции, время ожидания, объём ручных исправлений и лимиты Codex. Увеличение сверх 3 - отдельное решение владельца.

## Нельзя считать реализованным без фактической проверки

Подготовленный документ не равен автоматическому запуску Codex Desktop. Этот репозиторий не содержит работающего распределителя coding-сессий. Любой обещанный автономный запуск требует отдельной проверки доступных официальных возможностей Codex и соответствующего owner approval.
