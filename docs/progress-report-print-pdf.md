# Общий отчёт о прогрессе и печать в PDF

## Пользовательский контракт

Защищённая страница `/app/report` собирает единый фактический отчёт из уже существующих
источников прогресса. Пользователь открывает её из раздела «Прогресс», а тренер — из рабочей
области выбранного активного клиента. Период и субъект остаются в query-параметрах страницы,
поэтому reload и возврат из системного диалога печати не меняют контекст.

Поддерживаются `days_7`, `days_30`, `days_90`, `current_month`, `previous_month` и `custom`.
Произвольный период задаётся включительно через `date_from` и `date_to`, не может заканчиваться в
будущем и ограничен 366 днями. Backend остаётся источником границ в IANA-часовом поясе субъекта.

Данные возвращают два endpoint:

- `GET /api/v1/workouts/progress/report` — только текущий авторизованный пользователь;
- `GET /api/v1/coach/clients/{client_id}/progress-report` — только клиент с действующей связью
  тренер—клиент.

Для нативного TMA-download добавлены authenticated link endpoints:

- `POST /api/v1/workouts/progress/report/download-link`;
- `POST /api/v1/coach/clients/{client_id}/progress-report/download-link`.

Они валидируют тот же report context и возвращают короткоживущую HTTPS-ссылку на
`GET /api/v1/workouts/progress/report/file/{token}`.

В ответ входят общий adherence по `adherence-v1`, сигналы достаточности данных, плановые,
завершённые и пропущенные тренировки, рабочие подходы, внешний объём, рекорды, ручное кардио,
активная программа и блок, выбранная динамика упражнений, замеры тела, агрегаты дневника питания,
история целей, фактические weekly check-ins и дневные optional check-ins сна и настроения.
Дневной блок показывает только реально записанные дни, покрытие периода, распределение оценок и
осторожное направление тренда; частично заполненный день остаётся частичным. Расчёты переиспользуют
серверные сводки прогресса, тренировочной аналитики и питания; отдельной формулы для отчёта нет.

Пропуски не интерполируются. Незаполненный или неполный день питания не становится нулевым
рационом. Окружности сравниваются только с собственными замерами пользователя, а внешний объём не
используется как оценка техники, восстановления или готовности. Check-ins показываются как
самооценка, без медицинского диагноза и причинных выводов. Дневная запись привязана к локальной
календарной дате пользователя, допускает только ручное частичное заполнение и не обязательна.

## Передача отчёта текущему тренеру

На странице личного отчёта пользователь может явно передать отчёт только текущему тренеру с
действующей связью. Получатель не вводится вручную и не выбирается из произвольного списка. Передача
создаёт только внутреннее уведомление и описатель handoff: субъект, период и его часовой пояс,
версию контракта, доступные разделы, статус доставки и сведения для идемпотентного повтора. Ссылка
открывает авторизованный живой отчёт, поэтому повторное открытие показывает актуальные факты за
сохранённый период и отмечает изменение данных после отправки.

В handoff не сохраняются PDF, снимок отчёта, текст отчёта, личные заметки check-in, фотографии,
AI-текст или внешний адрес доставки. Backend повторно проверяет владельца, тренера и активную связь
при создании, открытии уведомления и повторе неудачной доставки. Повтор с тем же ключом безопасен,
а отправка новой версии получает новый ключ и не создаёт неявного read receipt. Границы MVP —
внутренний маршрут `/app/report`; Telegram, публичные ссылки и PDF-передача в этот контракт не
входят.

## Печать и Telegram Mini App

Первый релиз использует один HTML-документ и `@media print`. Кнопка «Печать / Сохранить как PDF»
открывает системный диалог браузера; интерфейс не называет HTML готовым PDF. Печатная композиция
всегда светлая, скрывает навигацию и элементы выбора, начинает каждую выделенную страницу-раздел
отдельной строкой с каноническим логотипом слева и периодом справа, задаёт A4, устойчивые поля,
повторяемые заголовки таблиц и явные разрывы крупных разделов. Нативный
CSS-счётчик страниц Chromium не используется, поскольку в системной печати он может вернуть `0`;
номер страницы остаётся возможностью конкретного браузера в его header/footer.

В Telegram Mini App системная печать не вызывается: действие «Скачать PDF» запрашивает ссылку для
точного периода и субъекта и передаёт её в `Telegram.WebApp.downloadFile`. Сервер отвечает готовым
`application/pdf`, `Content-Disposition: attachment`, CORS для Telegram Web и `no-store`. Старый
Telegram client без native download открывает ту же ссылку на файл через `openLink`; при отсутствии
обоих platform methods интерфейс оставляет обычную actionable ссылку. Внешний браузер больше не
должен восстанавливать TMA-сессию и не попадает на `/login`.

## Конфиденциальность и жизненный цикл

Отчёт вычисляется по запросу и не создаёт очередь, persistent PDF, временный файл или metadata в БД.
TMA download token зашифрован ключом, производным от `SECRET_KEY`, не раскрывает внутренние ID и
действует 5 минут. При скачивании backend повторно проверяет активность actor и, для client report,
активную связь тренер—клиент, затем заново строит отчёт в зафиксированных границах. Ссылка является
краткоживущим bearer capability и может быть повторно использована только в пределах TTL; ответ не
кэшируется. Сохранённая копия остаётся под контролем устройства пользователя.

Backend DTO не содержит auth-данные, user/workout/exercise ID, названия продуктов, приёмы пищи,
рецепты и закрытые комментарии тренера. Личная заметка дневного check-in не входит в aggregate,
PDF и trainer DTO; она доступна только владельцу записи и account export. Доступ тренера
проверяется при каждом запросе и прекращается вместе со связью. Маршрут приложения получает
`noindex, nofollow` через общий SEO-контракт
непубличных страниц. Обычные request logs могут зафиксировать обращение к endpoint и ciphertext
download token, но не его payload или содержимое отчёта; короткий TTL ограничивает окно риска.

Метаданные handoff входят в account export для владельца и тренера по соответствующей роли, но
экспорт также не включает сохранённый payload отчёта, revision или fingerprint. При удалении
аккаунта handoff удаляется вместе с его пользовательскими и relational данными.

Миграция `0069_daily_wellbeing_check_ins` добавляет одну строку на пользователя и локальную дату,
без фоновых worker и новых переменных окружения. PDF формируется `ReportLab` с
DejaVu Sans из runtime image; `cryptography` закреплена как прямая runtime dependency.
Миграция `0073_report_handoffs` добавляет только расширяемую таблицу описателей handoff и не
запускает внешнюю доставку или фоновые worker.

## Проверка

Контракт покрыт backend-тестами на совпадение канонических агрегатов, custom range и trainer
allow/deny/revoked. Frontend проверяет full/partial/no-data, длинные имена и заметки, историю цели,
доступные таблицы, 360/390 px, Dark TMA native download с точной ссылкой, fallback, светлую печать и
валидные A4 PDF Chromium/ReportLab. Backend отдельно проверяет attachment/CORS/no-store, invalid
token и отзыв trainer relationship после создания ссылки. Для handoff проверяются активная связь,
единственный текущий тренер, периоды и timezone, отсутствие payload/личных заметок, идемпотентное
создание, retry и stale notification destination; frontend проверяет preview, статус доставки и
повтор только неудачной попытки.
Рендер PDF проверяется постранично: контент не должен пересекать шапку или доступный браузеру
footer, крупные разделы не начинают страницу обрезанным заголовком.
