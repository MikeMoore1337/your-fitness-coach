# Контракт импорта питания: NI-01

**Версия:** `nutrition-import-v1`. **Область:** #881, подготовка контракта; не API и не
реализация импорта. Источники требований: [#881](https://github.com/MikeMoore1337/your-fitness-coach/issues/881),
[#880](https://github.com/MikeMoore1337/your-fitness-coach/issues/880); базовый код — `origin/dev`
`d37183fbff3c69ddf21b1e2df1117ab5f3da3664`.

Машиночитаемый контракт — `NutritionImportV1` в
[`nutrition_import.py`](../backend/fitminiapp_api/schemas/nutrition_import.py). JSON Schema можно
получить через `NutritionImportV1.model_json_schema()`; проверять данные нужно также через Pydantic,
поскольку не все межполевые ограничения выражаются в JSON Schema. Неизвестные поля отклоняются.
Версия меняется при несовместимом изменении; молча менять смысл существующего поля нельзя.
Контракт не зарегистрирован в приложении, не сохраняет данные и не разрешает запись в каталог.

## Что уже есть в YFC

- [`Food`](../backend/fitminiapp_api/models/food.py) — единый каталог с canonical facts,
  basis, provenance, качеством и довериями. `FoodDiaryEntry` хранит личную дату, приём пищи,
  количество и снимок нутриентов. `NutritionMealTemplate` ссылается на продукт или рецепт в
  личной области; он не создаётся по факту наличия импорта.
- [`nutrition_label/contracts.py`](../backend/fitminiapp_api/nutrition_label/contracts.py)
  задаёт имена нутриентов, единицы, основы и различие `read`/`derived`/неизвестно. Импорт
  использует те же имена и единицы; `potassium_mg` сохраняется для последующего решения, но
  отсутствует в текущем label-контракте и не становится незаметно canonical fact.
- [`food_catalog_contributions.py`](../backend/fitminiapp_api/services/food_catalog_contributions.py)
  уже содержит exact identity, обработку конфликтов и community contribution. Его текущие
  правила нельзя считать автоматически достаточными для всех источников и типов импорта.
  [`food_import.py`](../backend/fitminiapp_api/services/food_import.py) импортирует проверенный
  набор каталога и назначает `verified`; запускать его для пользовательской выгрузки нельзя.

Окончательная привязка к существующим сервисам, транзакции и ограниченные ресурсы — задачи
#882 и #883; CSV-адаптер — #884, PDF — #913, URL transport — #912. Этот контракт не создаёт
параллельные таблицы, каталог, дневник или автоматическую публикацию.

## Модель и соответствие полей

Числа в JSON передаются десятичными **строками** с точкой; `Decimal` сохраняет масштаб,
например `"12.30"`. Текущий предел — 18 цифр коэффициента без ведущих нулей, включая конечные,
и 8 десятичных знаков; входная строка ограничена 64 символами. Значение вне
этого диапазона, отрицательное, бесконечное или двоичный float отклоняется без округления;
адаптер должен вернуть ошибку с координатами, а не обрезать число. `null` не означает ноль.
Каждый известный нормализованный fact имеет `value`, единицу и `evidence=read|derived`; выведенный fact
дополнительно содержит код `derivation` и непустой список входов `derived_from`: каждый вход
задаёт имя поля и координаты источника, включая отдельную строку количества. Это позволяет
различать повторяющиеся строки; соответствие ссылок данным должен перепроверить будущий адаптер.
`absent`, `ambiguous`, `unreadable` требуют `value=null`. Отсутствующий объект fact тоже
означает неизвестное; явный ноль допустим только как прочитанный или обоснованно выведенный факт.
Это не сохраняет исходную строку числа: значащие нули сохраняются в `Decimal`, а исходная
лексическая форма и правила округления источника могут быть неизвестны.

| Контракт NI-01 | Смысл и связь с YFC |
|---|---|
| `schema_version` | Обязательная буквальная версия DTO. |
| `source.provider`, `source`, `source_version`, `adapter_version` | Поставщик, вид источника, известная версия экспорта и версия адаптера. Источники и адаптеры не являются `Food` и не повышают trust. |
| `source.source_format`, `transport` | Идентификатор формата и `upload`/`url`. Другой формат может использовать тот же DTO без изменения `Food`. Содержимое URL и токены в DTO не передаются. |
| `source.publication_rights` | `unknown`, `owner_reported`, `verified`, `prohibited`: описание состояния доказательств, **не** разрешение на запись от недоверенного клиента. `verified` требует отдельной проверки доверенным сервером в будущей реализации. |
| `coordinates.section`, `section_kind`, `page`, `row` | Нормализованная секция и позиции; page/row считаются с 1. CSV требует row, PDF — page. Позиция дополнительной строки количества хранится в `quantity_coordinates`. |
| `diary_date`, `timezone`, `meal_type` | Локальная календарная дата, известная IANA timezone или `null`, `breakfast`/`lunch`/`dinner`/`snacks` или `null`. Дата → `FoodDiaryEntry.diary_date`; timezone отдельного поля в записи дневника не имеет. Не подставлять московское время. |
| `food.name`, `brand`, `variant`, `kind` | Название/бренд → `Food.name`/`brand` только после проверки; вид явно отличает standard/branded food от `personal_recipe`, `arbitrary`, `unknown`. `variant` не является отдельным полем текущего `Food`; нельзя терять различие продукта и способа приготовления. |
| `food.identity_source`, `source_id`, `gtin` | Пара namespace/id или `null`; GTIN проверяется существующим `validate_gtin`. Могут сопоставляться с `Food.source_name`, `external_id`, `barcode` только после проверки происхождения. Одинаковый ID в разных namespace не доказывает идентичность. |
| `quantity`, `amount_unit`, `source_unit` | Фактическое количество и `g`/`ml`/`piece`/`serving` либо неопределённая единица. `FoodDiaryEntry.amount_unit` сейчас допускает `g`/`ml`/`serving`, поэтому `piece` требует доказанного отображения или отдельного решения, не прямой записи. |
| `serving_label`, `serving_measure` | Подпись и явно известная масса `g` или объём `ml` **одной** порции. Значения неизвестны → `null`; `ml` не является массой. Пригодные факты могут соответствовать `Food.standard_serving_*` или снимку дневника после отдельной проверки существующего контракта. |
| `nutrition.basis`, `facts` | `per_100_g` / `per_100_ml` / `per_serving` либо `null`; известные нормализованные факты требуют basis. Соответствуют `Food.nutrition_basis_*` и `canonical_facts`, но это ещё не готовый `CanonicalDraft`. Каждая единица проверяется по действующему словарю. |
| `original_totals` | Только прочитанные/неизвестные факты источника для `entry`, `meal`, `day`, `period` или неопределённого scope, с координатами и, если известны, датой и приёмом пищи. Факт сохраняет исходную единицу, в том числе `null` и приватную `source_unit` при неизвестной единице. Не подменяют canonical facts и не являются `Food`. |
| `diagnostics` | Безопасный машинный `code`, `warning`/`error`, координаты и имя поля. Не включать текст строки, названия, URL, рацион или исключение. Неоднозначность кодируется диагностикой и/или evidence. |
| `completeness` | `complete`, `partial`, `unknown` относительно документированной структуры; не означает, что в каждом дне периода есть записи. |

`FoodDiaryEntry` использует собственный nullable snapshot `nutrition_amount`; в нём `carbs_g`,
а в label/этом DTO — `carbohydrate_g`. Запись истории в #887 должна явно сопоставить имена,
проверить ограничения `Numeric`, единицы и отсутствующие значения. Исходные даты, даты summary,
индексы строк, состояния неизвестности и raw totals не имеют гарантированного lossless-места в
действующих таблицах. Сохранение их в будущем нельзя объявлять реализованным без отдельного
решения. `NutritionMealTemplateItem.amount_unit` и ссылка на `food_id`/`recipe_id` не делают
рецепт каноническим продуктом.

Показатели FatSecret сопоставляются по **проверенному имени заголовка и единице**, а не только
по номеру колонки. Ниже — целевые смысловые поля; наблюдённая структура одного CSV и границы
сопоставления описаны отдельно:

| Показатель источника | Поле факта DTO | Поле в существующем YFC |
|---|---|---|
| Calories / energy | `energy_kcal` или `energy_kj` по известной единице | `normalized_facts.energy_kcal` / `energy_kj`; diary snapshot `energy_kcal` |
| Protein | `protein_g` | `protein_g`; diary snapshot `protein_g` |
| Fat | `fat_g` | `fat_g`; diary snapshot `fat_g` |
| Carbohydrate | `carbohydrate_g` | `carbohydrate_g`; diary snapshot `carbs_g` |
| Fiber | `fiber_g` | `fiber_g`; diary snapshot `fiber_g`, может быть `null` |
| Saturated fat / sugar | `saturated_fat_g` / `sugars_g` | Одноимённые label facts; отдельного поля diary snapshot нет |
| Sodium / cholesterol | `sodium_mg` / `cholesterol_mg` | Одноимённые label facts; исходная единица total не предполагается |
| Potassium | `potassium_mg` | В текущем label vocabulary отдельного поля нет: не отбрасывать молча и не выдавать за сохранённый canonical fact |

Суффикс поля указывает целевую единицу нормализованного факта. В `original_totals` значение
хранится с реально прочитанной исходной единицей: например, натрий `0.120 g` не становится
автоматически `0.120 mg`. В `nutrition.facts` натрий допускается только в `mg`; переход в другую
единицу должен быть явным derived fact с указанными исходными данными.

## Сопоставление наблюдённого CSV с YFC

С разрешения владельца один CSV проверен локально в памяти: UTF-8 BOM, CRLF, разделитель CSV,
две именованные секции, ширина строк и типовые заголовки. Это проверка структуры одного файла,
а не спецификация всех версий FatSecret и не проверка адаптера. Значения, даты, названия продуктов
и строки из файла, путь к нему и сам файл не публикуются. Номера колонок ниже описывают только
наблюдённый вариант: будущий адаптер должен проверить заголовки, единицы и структуру.

| Часть источника | Соответствие и ограничение |
|---|---|
| Служебный заголовок и разделители | Метаданные отчёта; не `Food` и не запись дневника. Диапазон отчёта не имеет отдельного lossless-поля в v1. |
| `# Period Summary`: пять колонок | Текстовая метка и четыре значения: энергия, жир, углеводы, белок. Названия нутриентов соответствуют `SourceNutrients`, но см. ограничение семантики ниже. |
| Строки сводки по приёмам пищи и общий итог | Сводные строки, не продукты. Известный тип приёма пищи можно описать через `meal_type`; значение не становится `FoodDiaryEntry` или `NutritionTarget`. |
| `# Report Details`: одиннадцать колонок | Первая колонка содержит метку строки; остальные — показатели в таблице ниже. Раздел также содержит строки приёмов пищи с итогами, поэтому ширина 11 сама по себе не доказывает, что строка — продукт. |
| Строка продукта и следующая строка порции | Только после проверки контекста: название → `food.name`, порция → `quantity`/`amount_unit` и `quantity_coordinates`. Не выводить бренд, массу, плотность или идентификаторы из названия. |
| Даты, приёмы пищи и итоги в деталях | Дата и тип приёма пищи относятся к личной записи; достоверный итог — в `original_totals` с соответствующим scope. Сводки и разделители не создают `Food`. |

В наблюдённом варианте строка заголовка деталей содержит следующие смысловые колонки:

| Колонка | Показатель и единица | DTO / связь с YFC |
|---:|---|---|
| 1 | Метка строки | Контекст, дата, приём пищи, итог либо `food.name` после классификации; нельзя считать каждую метку продуктом. |
| 2 | Энергия, ккал | `energy_kcal`; для личной записи — `nutrition_amount.energy_kcal`. |
| 3 | Общий жир, г | `fat_g`; для личной записи — `nutrition_amount.fat_g`. |
| 4 | `Н/жир`, г | Предположительно насыщенные жиры → `saturated_fat_g`; обоснование и ограничение ниже. |
| 5 | Углеводы, г | `carbohydrate_g`; в снимке дневника имя `carbs_g`. |
| 6 | Клетчатка, г | `fiber_g`; отсутствие остаётся неизвестным. |
| 7 | Сахар, г | `sugars_g`; отдельного поля в снимке дневника нет. |
| 8 | Белок, г | `protein_g`; для личной записи — `nutrition_amount.protein_g`. |
| 9 | Натрий, мг | `sodium_mg`; не подменять солью. |
| 10 | Холестерин, мг | `cholesterol_mg`; отдельного поля в снимке дневника нет. |
| 11 | Калий, мг | `potassium_mg`; отдельного поля в текущем label vocabulary и снимке дневника нет. |

Строка продукта может содержать исходные значения для записанного количества; scope и basis
требуют подтверждения. Эти значения не становятся автоматически фактами `Food` на 100 г, 100 мл
или порцию. Для `Food.canonical_facts` и basis нужны допустимый источник, известная основа и
обоснованный пересчёт. `original_totals` сохраняет исходные единицы, а нормализованный факт —
единицу действующего словаря YFC.

**Сокращение `Н/жир`.** В публичной [русской таблице FatSecret](https://www.fatsecret.ru/%D0%BA%D0%B0%D0%BB%D0%BE%D1%80%D0%B8%D0%B8-%D0%BF%D0%B8%D1%82%D0%B0%D0%BD%D0%B8%D0%B5/%D0%B5%D0%B4%D0%B0/%D0%9F%D0%B8%D1%82%D0%B0%D1%82%D0%B5%D0%BB%D1%8C%D0%BD%D1%8B%D0%B5-%D0%9D%D0%B0%D0%BF%D0%B8%D1%82%D0%BA%D0%B8/%D0%B6%D0%B8%D1%80)
эта колонка стоит рядом с транс-, моно- и полиненасыщенными жирами; в соответствующей
[английской таблице](https://mobile.fatsecret.com/calories-nutrition/food/nutrition-drinks/fat)
ей соответствует `Sat`. [API FatSecret](https://platform.fatsecret.com/docs/v2/food_entries.get)
называет `saturated_fat` насыщенным жиром в граммах. Связь `Н/жир` с `saturated_fat_g` —
**вывод по сопоставлению локализаций**, а не опубликованное определение CSV-заголовка. Для
автоматической нормализации нужен подтверждённый профиль источника; до этого значение и его
семантику следует сохранить в приватном исходнике и показать как неоднозначность.

**Семантика сводки.** Заголовок наблюдённой таблицы содержит формулировку о суточной норме,
но сама она не доказывает, являются ли числа суммой, средним значением или целью. В v1 нет
поля для вида такой агрегации: `scope=period` его не заменяет, а `original_totals` предназначен
для достоверных итогов. Нельзя записать неопределённую сводку как итог за период, цель питания
или canonical facts. Значения такой сводки нельзя losslessly представить в v1; будущий адаптер
должен сохранить исходник в разрешённом приватном draft, выдать диагностику и не делать вид,
что они перенесены. Для представления таких сводок подготовлен отдельный
[контракт v2](nutrition-import-contract-v2.md). В v1 новое поле не добавляется: его старые
читатели отклоняют неизвестные поля.

## Нормализация входа

1. Адаптер отдельно проверяет допустимый формат, кодировку, заголовки и структуру. Для известного
   описания FatSecret ожидаются UTF-8 BOM/CRLF, `# Period Summary`, `# Report Details`, русские
   даты и приёмы пищи, 11-колоночные строки и отдельные одноколоночные описания порций. Один
   локальный файл подтвердил BOM, CRLF, секции, ширину заголовков, строки порций, десятичную
   запятую и пустые значения, но не универсальную грамматику. Не выбирать колонки только по
   позиции без проверенного заголовка и версии. Summary, разделители, заголовки и итоги никогда
   не становятся продуктами; DTO отклоняет food row вне `section_kind=detail`.
2. Известный адаптер с явно определённой локалью может разобрать дату, `1,5` либо `1.5` в
   `"1.5"`; CSV quoting и разделитель проверяются до обработки чисел. Смешанные и неоднозначные
   разделители, некорректные даты, неизвестные единицы и неполные строки дают диагностику;
   значение не угадывается. Исходная русская или английская дата не принимается как ISO DTO.
3. Если единица прочитана, но не сопоставлена, сохранить её как приватную `source_unit`,
   оставить `amount_unit=null` и потребовать разрешения неоднозначности. Отдельная строка порции
   относится к продукту лишь при доказуемой связи; иначе диагностируется. `piece` не равна
   `serving` без доказанного соответствия; `g` не равен `ml` без подтверждённой плотности.
4. Источник может содержать исходные totals за фактически потреблённое количество. Не записывать
   их автоматически как значения на 100 г или на порцию. Пересчёт допустим только при известных
   исходном scope, количестве, единице и совместимой основе; на 100 г из общей массы `m`:
   `source_total * 100 / m`, где `m > 0` в граммах. Аналогично для миллилитров. Сохранить
   source total и явно пометить derived fields и их входы. Не выводить массу, плотность,
   ингредиенты, GTIN или отсутствующие нутриенты из названия либо других нутриентов.
5. Сопоставлять исходные и рассчитанные итоги можно только для одинаковых scope, дат, единиц и
   полного набора составляющих. Сохранять оба значения и разницу. При неизвестном значении хотя бы
   одной строки итог непроверяем; неизвестное не считается нулём. Не заявлять «только округление»,
   если неизвестны точность **и** правило округления источника. При документированном правиле
   сравнивать возможные интервалы округления всех составляющих; несовпадение или невозможность
   сравнения показывать до confirm, не заменяя исходные значения. При переносе в YFC отдельно
   проверять точность его полей: здесь DTO не округляет до precision БД.
6. Одинаковые строки могут означать две порции, а не ошибку. Сохранить обе позиции и координаты,
   выдать предупреждение при необходимости; не удалять и не суммировать их автоматически.

## Детерминированная политика общего каталога

Это спецификация для #883, а не уже работающий matcher. Проверки идут по порядку; если несколько
условий применимы, выбирается первая строка. Любой результат относится к конкретной записи и
проверенной версии правил. Право на личный импорт оценивается отдельно.

| Условие | Результат и допустимое действие после будущего confirm |
|---|---|
| Источник запрещён либо право переиздания отсутствует/не проверено | `rights_blocked`: не публиковать и не переносить source facts в общий каталог. Сообщение владельца о разрешении FatSecret — `owner_reported`, не проверенный текст или лицензия. |
| `personal_recipe` или `arbitrary` | `personal_only`: личный путь, не shared `Food`; неизвестную классификацию не считать стандартным продуктом. |
| Идентичность или содержание конфликтуют, несколько кандидатов, неподтверждённая связь порции, fuzzy-only либо `kind=unknown` | `ambiguous`: ручное разрешение/карантин; существующие записи не менять. |
| Нет надёжной идентичности, допустимой основы/единиц или обязательных ккал, белка, жира и углеводов; ошибки/неразрешённые warnings качества | `insufficient`: не публиковать. Клетчатка может оставаться неизвестной. Значения и basis должны проходить действующую проверку `Food`, включая допустимые диапазоны и precision. |
| Ровно один действующий shared продукт с доказанной тождественностью и совместимыми фактами | `reuse`: переиспользовать без перезаписи, сохранив исходный provenance отдельно. `verified` существующего продукта не переносится на входящие данные. |
| Остался пригодный новый standard/branded product, источник и права разрешены, идентичность однозначна, конфликта нет | `new_candidate`: после явного подтверждения создать через существующий contribution path как `community_unverified`; без автоматического `verified`. |

Доказательство идентичности — корректная пара `(источник, стабильный ID)` с подтверждённой
семантикой или проверенный GTIN; проверенный alias допустим лишь в пределах доказанной идентичности.
Для продукта без GTIN/source ID допускается только утверждённое #883 детерминированное правило
для конкретной standard identity, явно включающее название, бренд при наличии, вариант,
приготовление и basis. Одно совпадение названия или разные namespace не доказывают совпадение;
fuzzy даёт лишь предложение. Проверка существующих функций нормализации не заменяет эти условия.
`per_serving` без массы не превращается в граммы и допускается как кандидат только при
однозначной идентичности самой порции; иначе `ambiguous`. Новые пригодные продукты не должны
ожидать произвольной ручной модерации, если все детерминированные условия и права выполнены.

Для воспроизводимого решения применять следующие условия, а не числовой confidence:

1. Разрешение и атрибуция должны быть подтверждены доверенной source policy; поле DTO само по
   себе не является таким подтверждением. `branded_food` требует непустой бренд; для standard food
   и товара нужны доказанные вид/вариант и identity по указанным выше правилам. Неизвестный вариант
   нельзя приравнять к отсутствующему, а текст `kind` из CSV не является доказательством.
2. Кандидаты ограничиваются активными общими `Food`. Если доказательная identity указывает более
   чем на один продукт или противоречит другому ключу, это `ambiguous`. Личные продукты другого
   аккаунта не участвуют в сопоставлении.
3. Совместимость для автоматического reuse: одинаковый вид и подтверждённые бренд/вариант,
   одинаковая basis и единица, присутствуют все четыре обязательных показателя, а каждое значение,
   известное обеим сторонам, численно равно при сравнении `Decimal` без округления. `12.30` и
   `12.3` равны как значения, хотя исходная точность сохраняется. Неизвестная клетчатка не равна
   нулю; при её отсутствии с одной стороны существующий факт не затирается. Любое различие
   известных фактов или несовместимая basis ведут к `ambiguous`, без допуска «на глаз».
4. `new_candidate` возможен только при нуле кандидатов по доказательной identity и наличии
   доказанного вида/варианта, разрешённого источника, basis и всех обязательных показателей.
   Отсутствие GTIN само по себе не запрещает стандартный продукт с проверенной identity. Если
   имеющихся доказательств не хватает, результат `insufficient` либо `ambiguous`, а не новая запись.

До будущей записи пользователь видит состав личных и общих изменений и явно подтверждает их.
#882 должен повторно проверить ownership, право, выбранные строки, версию draft и состояние
каталога, обеспечить идемпотентность и атомарность подтверждённого набора. История, дата, приём
пищи, количество, частота, автор и source file не попадают в общую карточку, аналитику, логи,
трейсы, Git или CI. `model_dump()` и Pydantic `ValidationError` могут содержать пользовательский
ввод: их нельзя записывать в журналы или отправлять во внешние сервисы без безопасного удаления
чувствительных значений. Нужны owner-scoped доступ, ограничение срока жизни и удаление source/draft,
а также согласованные export/delete/backup правила. Сроки и юридические условия здесь не
выдумываются; их реализация и проверка остаются будущей задачей.

## Синтетические образцы и границы проверки

[`backend/tests/fixtures/nutrition_import/`](../backend/tests/fixtures/nutrition_import/)
содержит вымышленные CSV на русском и английском, отрицательный образец и отдельно написанный
`neutral-golden.json`. Его строки демонстрируют DTO, а не являются результатом реально
существующего FatSecret parser. Синтетический пример пятиколоночной сводки и заголовка деталей
показывает структуру без записей пользователя; порядок не является спецификацией всех версий.
Периодный итог в `neutral-golden.json` — независимый вымышленный пример достоверного итога,
а не интерпретация этой сводки. Примеры содержат неполный период, отдельные строки порций,
повтор, разные единицы, пустые поля, `NaN`, ошибочную дату и разную ширину строк. Проверки DTO
дополнительно покрывают конфликт evidence, невозможную дату, неоднозначную basis, другой источник,
PDF-координаты, неподдерживаемые поля и запрещённые единицы.
