Этот документ не заменяет `AGENTS.md` или `docs/development.md`.

Сначала проверять этот проект и остальные проекты владельца, не создавать дубликат.

## Префиксы названий

Каждая Issue имеет ровно один префикс в начале названия:

| Префикс | Когда применять |
|---|---|
| `[Product Vxx]` | Эпики и задачи конкретной продуктовой версии, например `[Product V13]` |
| `[Bug]` | Функциональная или визуальная неисправность, в том числе мобильная и серверная |
| `[UI Backlog]` | Улучшение удобства, адаптивности или оформления, когда текущая работа корректна |
| `[Improvement]` | Улучшение существующей функции, не сводящееся к одному UI |
| `[Engineering]` | Архитектура, тесты, качество кода, производительность, технический долг |
| `[Operations]` | CI/CD, инфраструктура, резервные копии, развёртывание, мониторинг |
| `[Growth]` | SEO, конверсия, привлечение аудитории |

Префикс `[Fix]` не используется. Существующие `V11-*`, `V12-*` и `V13-*` остаются в своих версиях независимо от технической области. Код этапа (`V13-01`), если есть, сохраняется после префикса: `[Product V13] V13-01 - ...`. Избавляться от кодов задач и их исторических связей нельзя. Удаление прежних квадратных тегов происходит только после согласованной миграции.

## Иерархия и зависимости

- Epic - крупная цель с обязательными дочерними Issues; для связи используем встроенные Parent/Sub-issues.
- Task - самостоятельный проверяемый результат.
- Spike - исследование с вопросом, границами, альтернативами и выводом; дополнительная метка `spike`.
- Блокирующие зависимости - нативные Blocked by / Blocking. Простой контекст - ссылки Related без блокировки.
- Одна Issue - один основной результат, один ответственный PR. Сначала проверять открытые Issues/PR, не создавать дубликаты.

### Приоритеты

| Значение | Основание |
|---|---|
| P0 | Подтверждённая потеря данных, недоступность ключевого сервиса или критическая эксплуатируемая уязвимость |
| P1 | Существенно нарушен ключевой пользовательский сценарий либо заблокирована важная доставка; влияние и срочность описаны |
| P2 | Плановая необходимая работа; значение по умолчанию при отсутствии доказанной срочности |
| P3 | Необязательное улучшение с небольшим влиянием и допустимой отсрочкой |

Приоритет определяется по описанию, масштабу влияния, обходному пути, зависимостям, решениям владельца и актуальным доказательствам. Текст `[P1]` в заголовке сам по себе недостаточен. Приоритет не равен сложности, серьёзности дефекта или готовности к выпуску. Существующий обоснованный приоритет сохраняется; старые `P0 Critical` / `P1 High` / `P2 Medium` / `P3 Low` переименовываются без изменения уровня. Изменение уровня сопровождается кратким основанием в Issue или PR.

## Статусы

| Статус | Условие перехода |
|---|---|
| Backlog | Задача зарегистрирована; готовность или разрешение на начало ещё не подтверждены |
| Ready | DoR выполнен и работа разрешена владельцем в рамках действующей стадии |
| In progress | Разрешённая работа фактически началась |
| In review | Проверяются PR, критерии приёмки, результат DEV или выпуск; незавершённые условия остаются явными |
| Blocked | Продолжению мешает конкретная зависимость, HOLD, недоступный доступ или обязательное решение владельца |
| Done | DoD подтверждён для этого объекта; закрытие Issue и завершение PR проверяются отдельно |

Типовой путь: `Issue -> Backlog -> Ready -> In progress -> PR -> In review -> merge в dev -> DEV-приёмка -> release acceptance -> Done`. При блокировке возможен переход из любого незавершённого статуса в `Blocked`; после снятия возвращаются на подтверждённую стадию.

Открытый PR получает `In review`; отметка Draft и результаты Checks показывают его реальную готовность. Этот статус PR не переводит связанную Issue из `Blocked` или `Backlog` и не доказывает готовность к merge. Объединённый PR получает `Done` как завершённый PR. Родительская Issue остаётся `In review` либо `Blocked` до выполнения своего DoD.

Старый `In Progress` соответствует `In progress`, `Review` - `In review`. Для `Owner Approval` выбирают `Blocked` с указанием ожидаемого решения. Для `Release Check` проверяют текущие доказательства: `In review`, если идёт приёмка, либо `Blocked`, если выпуск упирается в конкретное условие. Старый `Done` не принимается без проверки незавершённых обязательств.

### DEV и production

Разработка идёт через отдельную ветку и PR в `dev`. Успешные проверки, merge в `dev`, установка Windows DEV и приёмка владельца - самостоятельные факты. Ни один из них не подтверждает production автоматически. Для runtime-изменений выпуск выполняется отдельным переходом `dev -> master`; нужны применимые разрешения, фактическая production revision и успешный smoke. Незавершённая V12 Issue остаётся открытой после DEV.

До production acceptance использовать `Refs #N` / `Related to #N`, когда автоматическое закрытие задачи преждевременно. Closing keywords вроде `Closes #N` в PR к default branch могут закрыть Issue при merge. Их применяют только когда такое закрытие соответствует DoD; отдельный workflow по статусу Project не должен закрывать Issues.

### Блокировки и неактивные выпуски

- Для `Blocked` записывают причину, ссылку на зависимость или требуемое решение, условие снятия и доступный следующий шаг. Нативные Blocked by / Blocking сохраняют; простую ссылку не превращают в блокировку.
- HOLD остаётся `Blocked` до нового решения владельца. Открытый PR, зелёный CI или давность HOLD не снимают его автоматически.
- Product V13/V14 сохраняют `Release=V13`/`V14`, но остаются `Backlog` либо `Blocked` до явной активации. Наличие в Release Planning не разрешает разработку.
- Для #830, #831 и #1201 действует перенос из V12 в Backlog/HOLD: `Status=Blocked`, `Release` пустой. Исторические ссылки и названия не стираются.
- Метки `gate:*` обозначают необходимость согласования, а не его получение. Подтверждение снятого gate хранится ссылкой на решение владельца.

## Definition of Ready (DoR)

1. Цель, контекст и ожидаемый результат понятны.
2. Критерии приёмки проверяемы.
3. Есть категория, обоснованные Status/Priority/Area; Release заполнен только при назначении выпуска.
4. Проверены блокирующие зависимости и разрешена продуктовая версия.
5. Проверены дубликаты и активные PR.
6. Все необходимые предварительные решения владельца получены.

Для Spike - вопрос, границы и ожидаемый материал вместо требований к готовой функции. Без DoR задача остаётся в Backlog или Blocked.

## Definition of Done (DoD)

1. Критерии приёмки выполнены.
2. Правила архитектуры и `AGENTS.md` соблюдены.
3. Нужные тесты добавлены/обновлены.
4. Обязательные Checks успешны на актуальном коде.
5. Проверены соответствующие регрессии.
6. Получены применимые согласования, PR интегрирован по действующим правилам.
7. Для runtime-изменений подтверждены развёртывание и production smoke.

Для исследований, документации и governance-изменений production не требуется; нужен принятый результат и соответствующие проверки. Epic закрывается лишь после завершения обязательных Sub-issues и общей приёмки.

## Границы автоматизации

- GitHub - единственный операционный источник истины. Никаких локальных очередей, controller, БД задач, обязательных зеркал и постоянных диспетчеров.
- Формы создают Issues; недостающие поля и нестандартные заголовки выдаются как замечания. Срочный инцидент можно зарегистрировать без полного отчёта.
- Проверки на совпадение названий и предполагаемые зависимости - подсказки, не автоматическое удаление или блокировка.
- Предварительный owner approval обязателен перед новым существенным визуальным решением; при необходимости повторяется перед выпуском. Скриншоты браузера не заменяют реальные проверки TMA/iPhone.
- Нельзя выполнять Product V11/V12/V13/V14 вне разрешённой стадии; никакой автоматической активации версии.
- Не делать автоматический merge/deploy или самостоятельный запуск следующей задачи без отдельного разрешения владельца.
- Публичные Issues не должны содержать секреты, токены, персональные данные или чувствительные детали уязвимостей.

## Представления доски

| Представление | Настройка | Что проверить |
|---|---|---|
| Board by Status | Board, группировка по Status; без фильтра, скрывающего Blocked или пустой Status | Видны все шесть статусов и незаполненные карточки |
| Priority Queue | Table, сортировка Priority от P0 к P3, Status и Area видимы; завершённые можно исключить | Заблокированные P0/P1 видны, неактивные выпуски не выглядят Ready |
| Bugs & Blockers | Table, все незавершённые элементы, группировка по Status, видимые Title/Labels/Priority/Area | Каждая Blocked-карточка видна, дефекты различимы по содержимому и меткам |
| Release Planning | Table, группировка по Release, видимые Status и Priority | Есть группа без выпуска; V13/V14 сохраняют неактивное состояние |
| In Review / PRs | Table, `status:"In review"`, видимые связанные PR, Draft, Checks и Reviewers по доступности | Открытые PR и Issues на проверке видны; Blocked проверяется в общей доске |

`Bugs & Blockers` намеренно охватывает больше, чем только дефекты. Фильтры по разным полям в Projects сочетаются через AND; `label:bug status:Blocked` скрывает блокировки без `bug`, а межполевая запись `OR` не даёт требуемого объединения. Не скрывать блокировки ради узкого фильтра и не вводить второй набор статусных меток. При необходимости дефекты временно отбирают внутри видимой очереди. Перед сохранением каждого представления проверяют контрольную Blocked Issue без bug-label, V13/V14 и Issue без Release.

## Штатные автоматизации GitHub Projects

Настройка ниже является целевой и требует проверки живыми событиями. Факт наличия YAML или включённого переключателя не подтверждает выполнение.

При создании Project GitHub по умолчанию включает переход в Done при закрытии Issue/PR и при merge PR. Перед переносом проверить эти настройки: автоматическое `Item closed -> Done` не подходит для продуктовой Issue без завершённой приёмки.

1. **Auto-add:** один workflow для `MikeMoore1337/your-fitness-coach` с условием `is:open`. Не добавлять `is:issue` или `is:pr`: один фильтр должен охватывать оба типа. Это позволяет обойтись одним штатным auto-add workflow; старые открытые элементы переносятся отдельно.
2. **Item added to project:** целевые значения - `Backlog` для Issue и `In review` для открытого PR. Сначала проверить в живом интерфейсе, можно ли настроить разные значения по типу. Если нет, оставить безопасный общий `Backlog`, переводить PR при триаже и явно указать ограничение в #1106. Не выдавать ручной перевод за автоматический.
3. **Pull request merged:** завершает только карточку самого PR (`Done`). Родительская продуктовая Issue не меняется по этому событию.
4. **Item closed:** использовать `In review` для проверки причин закрытия и DoD, если workflow доступен отдельно для Issues. После подтверждения приёмки ответственный ставит `Done`. Если типы нельзя разделить или правило перезаписывает `Done` у merged PR, оставить его выключенным и проверять закрытые Issues вручную. Это документируемое ограничение, а не полностью автоматизированное закрытие.
5. **Status -> close Issue** и автоматический `Done` для Issue по linked PR выключены. Не включать правила, снимающие HOLD или `Blocked` только по открытию/merge PR.

Закрытие с причиной `not planned` не доказывает выполнение: сохранить причину и проверить карточку вручную; при архивировании не представлять её как доставленный результат. При повторном открытии Issue пересмотреть Status и блокировки. Любое автоматическое изменение статуса проверяется вместе с текущими условиями, включая гонку `Item closed` / `Pull request merged`.

Штатные defaults не определяют достоверные Priority, Area и Release из произвольного текста. Эти поля заполняются при триаже, с проверкой уже назначенных значений. Не добавлять постоянный процесс, платный сервис или независимый контроллер ради такой классификации. `.github/workflows/issue-governance.yml` остаётся read-only проверкой рекомендаций и не управляет жизненным циклом.

## Разовый перенос и проверка

Миграция #1106 разрешена владельцем в заданном объёме. [Прежний обзор миграции](issue-governance-migration-review.md) сохраняется как историческое обоснование; он не становится новым обязательным индексом состояния.

1. Авторизованно перечислить проекты владельца, проверить проект №1, владельца, привязку к YFC, текущие поля, Views и workflows. Не создавать второй Project при недоступности существующего.
2. Получить все страницы актуальных открытых Issues и PR непосредственно из GitHub; отдельно посчитать оба типа. Закрытые архивные задачи массово не импортировать.
3. Сопоставить карточки по стабильному GitHub content ID / URL, проверить дубли и сохранять существующие карточки. Повторный запуск не должен создавать второй элемент для той же Issue/PR.
4. Прочитать текущее содержание, важные комментарии, решения владельца, зависимости и назначенные поля. Выставить обоснованные Status/Priority/Area/Release; неоднозначности не разрешать эвристикой по заголовку. Сохранить номера, историю, native dependencies и ссылки.
5. При обновлении single-select значений сохранять option IDs, если API это позволяет. Не удалять старую опцию до переноса всех использующих её карточек; проверить и закрытые исторические элементы существующей доски без нового массового импорта.
6. Проверить полный путь на разрешённых существующих или безопасных временных объектах. Подтвердить auto-add новой Issue и PR, поля, видимость зависимостей и HOLD, merge PR, сохранение незавершённой parent Issue, закрытие/повторное открытие Issue и отсутствие дублей при повторном запуске. Временные объекты явно пометить, завершить и убрать из рабочей очереди штатным архивированием.
7. Опубликовать в #1106 реальный URL, количество Issues/PR, доказательства настройки и живых событий. Закрывать #1106 только после выполнения всех её критериев; подготовленные команды не являются выполненными операциями.

Проверка одноразовая: не создаются Markdown-реестр, локальная очередь, обязательное зеркало или служба синхронизации. После запуска очередь и поля ведутся в самом Project.

## Проверка доступа и заполненности

Для работы достаточно авторизованного GitHub UI или штатного `gh` с доступом к нужному Project. На уже авторизованном компьютере доступ проверяют без вывода токена:

```bash
gh auth status
gh project list --owner MikeMoore1337 --limit 100 --format json
gh project view 1 --owner MikeMoore1337 --format json
gh project field-list 1 --owner MikeMoore1337 --format json
```

Если существующему OAuth-входу `gh` не хватает прав на запись Projects, владелец может добавить scope через `gh auth refresh -s project` в своём терминале и штатное окно GitHub. Не просить секреты в чате, не печатать `gh auth token`, не копировать личные токены в репозиторий или Actions. Обычный `GITHUB_TOKEN` репозитория не предоставляет доступ к пользовательскому приватному Project.

`scripts/issue_project_fields.py` остаётся необязательным **read-only** помощником. Перед применением к новой схеме проверить, что используемая версия поддерживает её название и значения. Старая версия с обязательным `Effort` и `YFC Development` не является проверкой новой схемы. Отсутствие доступа или несовместимость явно отмечают; локальный тест не заменяет живое чтение карточек.

После доставки совместимого обновления помощника в рамках #1106 доступны следующие проверки:

```bash
# Полное покрытие открытых Issues и PR, допустимые поля и дубликаты:
python scripts/issue_project_fields.py --schema delivery --strict

# Проверка конкретной Issue после создания/триажа:
python scripts/issue_project_fields.py --schema delivery --issue 123 --strict

# Проверка Issue или PR с машиночитаемым результатом:
python scripts/issue_project_fields.py --schema delivery --item 123 --strict --format json

# Чтение старой схемы до переноса, без изменения карточек:
python scripts/issue_project_fields.py --schema legacy
```

Режим `legacy` нужен для сравнения со старой доской; его PASS не завершает миграцию на `delivery`. Для новой схемы обязательны Status/Priority/Area, пустой Release допустим, а Effort не является условием успеха. Помощник проверяет фактические значения, но не меняет их и не закрывает Issues.

Живая проверка должна сопоставить все открытые Issues/PR со всеми карточками, проверить допустимость и заполненность Status/Priority/Area, разумность Release, отсутствие дублей и ложного `Done`. Открытая Issue с `Done`, закрытая без доказанного DoD или merged PR, перезаписанный обратно в review, требуют разбирательства. Заполненность полей не доказывает правильность приоритета, приёмку или production delivery.
