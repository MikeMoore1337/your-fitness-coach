# Периодические отчёты по питанию

Отчёт внутри раздела «Прогресс» показывает фактически подтверждённые итоги дневника и
сопоставляет каждый день с той версией цели КБЖУ, которая действовала в эту дату. Frontend не
загружает отдельные записи продуктов ради агрегации.

## API и периоды

- `GET /api/v1/workouts/progress/nutrition-report` — JSON-отчёт текущего пользователя;
- `GET /api/v1/workouts/progress/nutrition-report.csv` — тот же отчёт в CSV;
- `GET /api/v1/coach/clients/{client_id}/nutrition-report` и вариант с `.csv` — отчёт активного
  клиента тренера через существующую проверку связи тренер—клиент.

Параметр `period` принимает `days_7`, `days_30`, `days_90`, `current_week`, `current_month`,
`previous_month` или `custom`. Скользящие периоды включают текущий локальный день. Текущая неделя
начинается в понедельник, текущий месяц — первого числа, прошлый месяц возвращается полностью. Для
`custom` обязательны `date_from` и `date_to`; будущие даты, обратный диапазон и окно длиннее 366
календарных дней отклоняются с `422`.

Границы и признак текущего дня рассчитываются в IANA-часовом поясе владельца данных. При запросе
тренера используется часовой пояс клиента.

## Полнота и расчёты

Дневная серия различает четыре состояния:

- `complete` — пользователь подтвердил заполненный день;
- `fasted` — пользователь явно подтвердил день без приёмов пищи; только здесь нулевые КБЖУ
  являются фактом;
- `incomplete` — записи есть или день явно оставлен незавершённым;
- `missing` — ни записей, ни явного статуса нет; КБЖУ возвращаются как `null`, а не как ноль.

`logged_days` равен сумме `complete` и `fasted`, `eligible_days` — числу календарных дней периода,
а `coverage_percent` описывает их отношение. Средние, минимумы, максимумы и сравнение с целью
используют только подтверждённые дни. Незавершённый текущий день остаётся в дневной серии, но не
входит в средние. Quick Add хранит либо полный набор Б/Ж/У, либо ни одного макронутриента. Во
втором случае Б/Ж/У этого дня остаются `null`, а не подменяются нулями.

Для каждого дня backend выбирает цель по полуоткрытому effective-интервалу
`[effective_from, effective_to)`. Поэтому средняя цель и отклонение не подменяют исторические
версии текущей целью. Калорийный факт использует существующую границу `+-10%`, белковый — факт
достижения ориентира. Для жиров и углеводов возвращается только числовое сравнение без отдельного
adherence score.

Отчёт не делает выводов о здоровье, витаминах, качестве рациона или причинах изменения веса.

### Клетчатка и объяснимые отклонения

Поле `daily[].fiber_g` отражает сумму клетчатки из подтверждённых записей.
Если хотя бы у одного продукта данного дня клетчатка неизвестна, итог дня
остаётся `null`, а не подменяется нулём. Для явно подтверждённого дня без еды
`fasted` допустим ноль. `summary.fiber_g` вычисляется только по подтверждённым
дням с известной клетчаткой и показывает `sample_days`. Цели клетчатки в YFC
сейчас нет: в отчёт **не** добавляется несуществующая целевая норма или диагноз.

`insights[]` - пояснения для чтения, без изменения целей или дневника.
Тренд формируется только при наличии минимум трёх завершённых дней, составляющих
не менее 60% выбранного периода. Для каждой метрики требуется наличие факта и
действовавшей тогда цели минимум в трёх днях и в 60% завершённых дней.
Отклонение считается **по дневной исторической цели**, а не по текущей.
Устойчивым считается однонаправленное отклонение более 10% для калорий и более
15% для БЖУ как минимум в трёх днях и 70% сопоставимых дней.
Неполные, отсутствующие и намеренно голодные (`fasted`) дни **не** используются
для таких выводов. Возвращаются направление, число наблюдений, средняя разница,
код действия и русскоязычное объяснение. Отчёт не делает медицинских выводов.

`open_meal_suggestions` - указание открыть **существующий** движок подбора
сохранённых продуктов, рецептов и шаблонов, а не новый генератор.
`review_portions` - предложение проверить записи/порции/цели без автоматической
коррекции. Визуальное отображение этих данных требует отдельного owner approval.

## CSV и изоляция данных

CSV начинается с UTF-8 BOM, содержит одну строку `summary` и строки `daily`. Стабильные machine
columns включают границы периода, дату и статус дня, фактические и целевые КБЖУ, отклонения,
булевы признаки калорийного диапазона и белковой цели, marker смены цели и показатели coverage.
Строковые значения, которые могут быть интерпретированы табличным редактором как формула,
принудительно записываются как текст.

Экспорт не содержит названий продуктов, приёмов пищи, заметок или чужих пользовательских данных.
Личный endpoint всегда использует авторизованный `user_id`. Trainer endpoint сначала подтверждает
активную связь; посторонний или бывший тренер получает `404`.

## Производительность и хранение

Длина отчёта ограничена 366 днями. Backend выполняет три ограниченных запросом периода чтения:
агрегацию записей по `diary_date`, загрузку явных статусов дней и загрузку пересекающихся версий
цели. Дневная серия формируется в памяти только внутри этого ограниченного окна. Используются
существующие индексы и effective-history из целей питания; новая migration не требуется.

Отчёт вычисляется по запросу: отдельная persistent metadata и PDF-артефакт не создаются. Account
portability export включает принадлежащие пользователю записи дневника и историю целей, из которых
строится отчёт, но не временный render. Если persistent report metadata появится позже, она должна
быть отдельно включена в account export/delete inventory.
