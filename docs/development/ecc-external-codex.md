# ECC при разработке YFC - внешний оригинальный плагин Codex

Связано с [#1291](https://github.com/MikeMoore1337/your-fitness-coach/issues/1291) и upstream [affaan-m/ECC](https://github.com/affaan-m/ECC). **Статус 2026-10-27: SOURCE_ONLY / LIVE_CODEX_NOT_VERIFIED.** Это инструкция для разработчика, а не часть веб-приложения, бота, сборки, БД или production.

## Что переиспользуется «как есть»

- Оригинальный ECC Codex plugin **из единственной пользовательской установки**; проверенный upstream commit `25278e7d7b6cf6e6a4e7a6c8e10f14ff22f0eb5b`, plugin version `2.2.3`. [Исходный манифест](https://github.com/affaan-m/ECC/blob/25278e7d7b6cf6e6a4e7a6c8e10f14ff22f0eb5b/.codex-plugin/plugin.json). Версия действующей установки пока неизвестна.
- YFC **не** создаёт локальную копию ECC и не повторяет его навыки в `.agents/`/CI. Подключение через поддерживаемый графический Codex Desktop, вне репозитория; где оно отсутствует, использовать существующие инструменты разработки, а не имитировать ECC.
- Не расширять права плагина на production browser, cookie, network или домашние файлы. У upstream по умолчанию определён `chrome-devtools` MCP с `npx -y chrome-devtools-mcp@1.10.1`; `SessionStart` hook - исполняемый Node bootstrap. Оба компонента требуют отдельной проверки/разрешения, установка skills не означает автоматического доверия.
- Оригинальные TDD/review/verifier-навыки - опциональные подсказки процесса. Нельзя подменять ими канонические `AGENTS.md`, `scripts/agent_harness.py`, существующие pytest/Vitest/Playwright или GitHub Checks. Базовые ограничения задач и права пользователя всегда первичны.

## Узкая приёмка только в DEV

1. Убедиться, что YFC `dev` чистый, подключён к разрешённой синтетической локальной БД, и пользовательский `CODEX_HOME` содержит только **один** действительный ECC plugin (если вообще содержит). Записать отображаемую версию Codex Desktop и плагина, но не публиковать секреты/частные пути/логи с пользовательскими данными.
2. После согласования hook/MCP прав запустить один **исходный** ECC `tdd-workflow` или `code-review` на коротком искусственном dev-only примере и проверить, что его поведение реально наблюдалось. Не выдавать появившийся пункт каталога за запуск. Не включать агентные фоновые работы.
3. Сравнить вывод с действующими правилами тестирования YFC, проверить targeted pytest/Vitest/Playwright и отсутствие изменения бизнес-логики, API, миграций, активных тренировок, пользовательских данных и security gates. Вся локальная тестовая информация должна оставаться в DEV.
4. Отключение - штатный UI Plugins; в новой сессии проверить, что ECC не активен, а обычная разработка и `scripts/agent_harness.py` по-прежнему доступны. **Не** удалять общую директорию `CODEX_HOME` или данные соседних проектов.
5. Все допустимые изменения по этой задаче идут в PR на `dev`, только после зелёных Checks. **Никаких merge в `master` и production release** из этого Issue.

## Что не считается выполненным

Ни одна запись в этом репозитории не устанавливает внешний плагин Codex. До реального smoke в Codex Desktop статус подключения = `NOT_VERIFIED`. Уточнение по оригинальной установке, разрешениям и откату: [Toolkit #424](https://github.com/MikeMoore1337/ai-development-toolkit/issues/424), [ECC Codex README](https://github.com/affaan-m/ECC/blob/main/.codex-plugin/README.md). Защищённый YFC `dev`/CI и имеющийся [Agent Harness](../agent-harness.md) остаются основным контрактом разработки.
