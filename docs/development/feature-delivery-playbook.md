# Разработка функций и доказательная приёмка в YFC

Назначение: улучшать проработку неоднозначных и многокомпонентных задач Codex, не создавая новый жизненный цикл. Это **не** контроллер, новый CI-gate, task database, замена GitHub Issues или автоматическое разрешение на разработку следующей задачи.

## Когда применять

Сначала прочитать текущий запрос владельца, Issue и связанные решения, актуальный код и тесты. Найти уже существующий путь; не делать отдельное исследование, если решение очевидно.

Выбрать **минимальную глубину анализа**, а не дополнительную систему исполнения:

| Ситуация | Действие |
| --- | --- |
| Точечная, обратимая правка с ясными критериями | Непосредственно исправить, выполнить адресную регрессию, описать результат в PR. Отдельный план и дополнительные агенты не нужны. |
| Новое поведение, связанное с несколькими компонентами | Кратко указать критерии, затронутые контракты и риск в существующем Issue/PR; затем реализация и проверки. |
| Права доступа, пользовательские данные, миграция, платежи, непроверенная интеграция или существенное изменение UI | Сначала проверить решающее допущение и применимый owner/legal/security/visual gate. Не переходить границу согласования под видом подготовки. |

Это не числовые бюджеты времени или вызовов. Не утверждать экономию токенов без реальных данных Codex.

## Минимальный контракт задачи

Для сложной задачи в **каноническом Issue**, а не в параллельном локальном журнале, достаточно зафиксировать:

1. Наблюдаемое исходное поведение и ожидаемый результат, включая роль и поверхность (Web, TMA, backend, bot).
2. Проверяемые критерии `C1`, `C2` и т. д.: вход -> действие -> результат, а также релевантные ошибка, повтор, восстановление, права и сохранение.
3. Затронутые источники истины/API/миграции, явно исключённые изменения и существующие тесты.
4. Критический риск и минимальную проверку, которая действительно могла бы опровергнуть решение.

Если требования уже определены, не переписывать Issue в новый PRD. Для продуктовой неопределённости использовать `$product-discovery`; для тестовой стратегии - `$qa-engineer` и подходящие узкие skills. GitHub Issue, Pull Request, Checks и Actions остаются единственным операционным источником состояния.

## Реализация и проверка

- Для воспроизводимого дефекта сначала показать сбой на старом поведении, затем исправить причину и запустить относящуюся к ней регрессию. Для документационных изменений не имитировать TDD.
- По каждому существенному `C*` указать подтверждающее evidence: команду/сценарий, результат, окружение, SHA/CI run. Проверка существования файла не равна проверке пользовательского сценария.
- Для записи пользовательских данных проверять сохранение и чтение обратно, а не только HTTP 200 или оптимистичный интерфейс.
- Проверять отрицательные сценарии и межролевой доступ там, где они относятся к затронутому контракту.
- Локальные unit/integration/E2E-проверки, synthetic/mock-сценарии, CI на exact SHA, Mobile Web, mocked TMA, реальный Telegram и production deployment/smoke фиксировать раздельно; выбирать только относящиеся к риску уровни. Локальный или mock-результат не доказывает live/production-поведение; неподтверждённое не называть проверенным.
- Независимый взгляд при значимом риске получать через существующие проверки, профильные QA/security skills или согласованное ревью PR. **Не** вводить обязательного нового reviewer agent или круги проверок для каждой правки.
- После исправления замечания повторить только затронутые проверки и необходимые сквозные сценарии. Не повторять полный аудит без изменения оснований.

## Пример приёмки

Для изменения завершения подхода:

- `C1`: подтверждённое завершение сохраняется после обновления страницы (тест и чтение состояния).
- `C2`: повторное нажатие не создаёт дополнительного завершения/таймера (отрицательный/идемпотентный сценарий).
- `C3`: на Mobile Web и mocked TMA нет непредусмотренной прокрутки и потери ввода (браузерные доказательства). Реальный Telegram остаётся `NOT_VERIFIED`, пока его не проверили.

Это пример структуры, а не заявка на выполнение или изменение существующей задачи.

## Завершение и границы

В PR кратко перечислить `C*` со статусом `VERIFIED` / `NOT_VERIFIED` / `BLOCKED`, фактические команды и CI, известные регрессии и необходимые owner gates. Отчёт исполнителя не заменяет CI или фактическую проверку. Не создавать локальную БД, очередь, зеркала Issues, новые обязательные файлы состояния, авто-merge/deploy, дополнительные сервисы или зависимости ради этой методики.

Визуальная работа следует существующему порядку: конкретный макет -> публикация в Issue -> явное согласование владельца -> реализация -> финальные реальные AFTER-доказательства -> визуальная приёмка владельца -> отдельное разрешение на выпуск. Этот документ не меняет `AGENTS.md`, `docs/ISSUE_GOVERNANCE.md`, действующие QA/security skills, решения владельца и требования к PR, CI и выпуску; при конфликте действует более приоритетное правило.
