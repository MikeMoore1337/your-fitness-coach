# Периодизация программ: доменный контракт #916 / #919 / #920

Программа остаётся в существующем домене `ProgramTemplate → UserProgram → UserWorkout`, с `ProgramRevision` для истории плана. UI #918 не входит в эти изменения.

## Назначение и источник плана

`week_cycle` — необязательное поле создания шаблона: `schema_version=1`, положительное `length_weeks` (K), явное `repeat`, необязательные `week_types` (`light`, `medium`, `heavy`) длиной K. Отсутствие поля сохраняет legacy-поведение. Тип недели не означает deload, восстановление или автоматическую прогрессию.

Срок назначения N независим от K. При `repeat=true` исходная неделя равна `((absolute_week - 1) % K) + 1`; при `repeat=false` N не может превышать K. Неполное последнее повторение и N<K допустимы. Полный исходный цикл хранится в `logical_cycle` снимка назначения, включая упражнения, недельные предписания, группы и роли подходов. Он не зависит от числа созданных тренировок и дальнейшего редактирования шаблона.

При назначении создаётся окно до четырёх недель. Логический срок не ограничен 24 неделями. Сохраняются ограничения HTTP-запроса, существующий бюджет 20 000 плановых сегментов на снимок/операцию и поддерживаемый диапазон календарных дат. Это операционные ограничения, а не новый предел длительности программы.

У opt-in тренировок есть `source_cycle_week`, `cycle_iteration`, `plan_revision_number` и `plan_materialized`. Частичный уникальный индекс защищает `(user_program_id, week_number, day_number)`; legacy-записи с пустой lineage под него не подпадают.

## Расписание и выполнение

`/today` готовит рабочее окно; `/week` и `/schedule` создают отсутствующие записи расписания в запрошенном диапазоне, до 93 дней. Такие записи имеют постоянные ID, но будущие упражнения и подходы заранее не создаются. Они материализуются при открытии/старте тренировки или попадании в рабочее окно. Перенос меняет дату, сохраняя абсолютную неделю и идентичность вхождения.

GET-запросы могут записывать это ограниченное представление расписания. Создание и чтение актуального плана сериализуются блокировкой `UserProgram`; уникальный индекс остаётся защитой БД. Изменения фиксируются только после успешного построения окна. При ошибке незавершённая транзакция откатывается; повтор не создаёт дубликаты.

Материализация при чтении использует отдельную SQLAlchemy Session на том же Engine. Она не фиксирует и не откатывает посторонние dirty/flushed изменения вызывающей Session. Ошибка откатывает только создаваемое представление. Перед стартом план повторно читается под блокировкой программы в транзакции самой записи, без промежуточного commit.

Старая незавершённая тренировка остаётся незавершённой и не мешает построению нового окна. Пропущенные промежуточные недели не исчезают из логического плана. Автоматическое завершение проверяет полноту всех предусмотренных недель и дней, а не только отсутствие активных физических записей.

Планировщик напоминаний готовит ограниченное расписание opt-in программ без подходов, даже если пользователь давно не открывал приложение. Pause/resume, skip и reschedule сохраняют существующие права и lifecycle-правила.

Сводка тренера считает тренировки по полному логическому плану. Аналитика учитывает ещё не созданные пропущенные вхождения в числе запланированных тренировок, сохраняя фактические показатели только за выполненные подходы. Перенесённое вхождение учитывается по новой дате; подходы ради расчёта не создаются.

## Области правок

Существующий `POST /programs/assigned/{id}/exercises` принимает `expected_revision_number`, исходную позицию упражнения и день программы. Для циклов доступны:

- `occurrence_weeks: [8]` — только указанное вхождение;
- `from_week: 8, source_cycle_week: 2` — будущие повторения исходной недели 2 с выбранной границы;
- `from_week: 8` — все будущие вхождения позиции упражнения;
- существующие `next_workout`, `current_block`, `future_program` — с прежними смыслом и проверками области.

Нельзя совмещать конкретный список недель с повторяемой областью. Новые номера недель строго целочисленные. Последняя разрешённая ревизия имеет приоритет внутри своей области; исторические ревизии не переписываются. Область исходной недели привязана к фазе конфигурации: изменение K не перепривязывает её молча к другой исходной неделе. Конкретные вхождения и область всех будущих повторений продолжают действовать для сохранившейся исходной позиции.

Правки применяются к `planned` тренировкам и ещё не созданным неделям. У уже созданных упражнений и подходов сохраняются ID, пока структура допускает это. Изменение плановых целей повышает версии существующих подходов; устаревшая offline-мутация отклоняется существующим контрактом синхронизации. После исчерпания бюджета пересчёта запись сохраняет прежний `plan_revision_number` и обновляется под блокировкой при чтении/старте.

Начатые тренировки и записанные факты этим API не заменяются. Для разрешённых изменений `in_progress` действует существующий versioned live-workout API. Завершённые результаты, RIR, отказ, даты и версии не пересчитываются.

Внутренний nullable `UserWorkoutSet.plan_version` хранит последнюю версию, изменённую только планом. Повторная правка плана разрешена, пока `version` совпадает с этим маркером. Фактическая мутация повышает `version`, сохраняя маркер; даже последующая очистка факта не разрешает перезаписать историю. Для legacy `NULL` сохраняется консервативная защита по версии.

## Ревизия срока и структуры

`PATCH /programs/assigned/{id}/cycle` требует `expected_revision_number` и `effective_from_week`. `duration_weeks` явно меняет N. `source_week_order`, например `[1,2,3,1]`, задаёт новый конечный цикл из исходных недель предыдущей конфигурации; новая фаза начинается на указанной границе. Необязательные типы недель можно указать заново или явно убрать через `week_types: null`.

Граница не может затрагивать исторические или начатые вхождения. Сокращение срока отменяет только будущие плановые записи за новой границей, сохраняя их ID. Повторное расширение восстанавливает допустимые текущим планом вхождения, отменённые изменениями самого плана. Старые факты и снимки сохраняют прежнюю идентичность.

`/schedule` и `/week` исключают отменённые вхождения из календаря. Причина структурной отмены также сохраняется в ревизии: возврат дня или увеличение срока восстанавливает только отменённые самим планом вхождения, допустимые текущей конфигурацией. Отмены по другим причинам и пользовательские пропуски не восстанавливаются. Область `next_workout` сначала строит ближайшее ограниченное окно, затем выбирает ближайшее логическое вхождение.

Restart создаёт новое назначение с полным логическим источником, конфигурациями и применимыми overrides по тем же абсолютным номерам недель. Даты пересчитываются от нового начала; старые переносы и фактические результаты не копируются. Повтор блока использует логический план блока, даже если его будущие тренировки ещё не материализованы. Импорт будущего плана также записывает конфигурационную ревизию, сохраняя историческую часть назначения. Публичный снимок шаблона и его приватная копия сохраняют `week_cycle`; экспорт аккаунта включает полный источник и историю ревизий.

## Хранилище и проверка

Миграции 0134–0136 добавляют nullable lineage, concurrent partial unique index и заменяют CHECK с верхним пределом 24 на положительный домен. Для legacy `plan_materialized=NULL` означает материализованный план. Downgrade отказывается удалять используемую lineage или восстанавливать предел 24 поверх длинных программ; нужен forward-fix.

Существующая блокировка мигратора использует тот же PostgreSQL advisory key на уровне сессии: autocommit при создании индекса не освобождает её. После успеха или ошибки блокировка снимается. Для программного вызова Alembic переданное соединение должно завершить текущую транзакцию. Индекс после concurrent build проверяется на валидность; незавершённый индекс останавливает миграцию и требует ремонта перед повтором. Online checker допускает только точный запрос этих признаков создаваемого индекса, а остальные SQL-вызовы остаются запрещены. Downgrade 0135 возвращает исходную схему без нового CHECK длительности, что сохраняет полный replay старых миграций.

Основные приёмочные тесты: `test_program_cycle_domain.py`, `test_program_week_cycle.py`, `test_program_lifecycle.py`. `test_program_cycle_storage_migration.py` проверяет ограничения, сохранение фактов и защиту downgrade. `test_program_cycle_concurrency.py` содержит реальные конкурентные транзакции и пропускается на SQLite.

Для PostgreSQL используйте отдельную disposable БД: `TEST_DATABASE_URL` заставляет pytest пересоздавать её схему. Никогда не указывайте DEV или production. Пример проверки: `python -m pytest backend/tests/test_program_cycle_concurrency.py -q`; для полного replay Alembic запускайте `python -m alembic upgrade head` из `backend/` с синтетической конфигурацией отдельной базы.

Технический PASS не означает согласование UI, готовность независимого ревью, merge или deployment. В рамках этой работы разрешён только dev; master и production требуют отдельного решения владельца.
