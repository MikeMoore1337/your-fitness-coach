## 2. Анализ производительности

Исследуй следующие направления.

### 2.1. Загрузка JavaScript и CSS

Проверь:

- размеры начальных JS/CSS-файлов;
- размеры отдельных чанков;
- дублирование зависимостей;
- эффективность tree shaking;
- code splitting;
- lazy loading маршрутов и тяжёлых компонентов;
- повторную загрузку модулей;
- ненужные зависимости в начальной загрузке;
- динамические импорты.

Используй существующие Vite-инструменты и скрипты проверки производительности.

Не добавляй новые зависимости без подтверждённой необходимости.

Цель - устранить подтверждённые проблемы и добиться прохождения обоснованных бюджетов производительности без искусственного повышения лимитов.

### 2.2. React и TanStack Query

Проверь:

- лишние повторные рендеры;
- дорогие вычисления внутри компонентов;
- некорректную мемоизацию;
- нестабильные зависимости хуков;
- дублирующиеся API-запросы;
- неправильную инвалидацию Query;
- избыточные refetch;
- некорректную работу staleTime;
- лишние сетевые запросы при переключении экранов;
- деградацию после возврата приложения из фонового режима.

Не добавляй `useMemo`, `useCallback` и `React.memo` повсеместно. Оптимизируй только подтверждённые проблемные места.

Не допускай появления устаревших данных после изменений логики кеширования.

### 2.3. Основные разделы приложения

Приоритетные пользовательские сценарии:

1. Авторизация и первоначальная загрузка.
2. Сегодня.
3. Активная тренировка.
4. Программы тренировок.
5. Энциклопедия упражнений.
6. Питание.
7. Прогресс и статистика.
8. Coach OS.
9. Публичный Landing.
10. Навигация Web/PWA/TMA.

Особое внимание удели мобильным устройствам.

Для каждого подтверждённого узкого места определи источник проблемы и предложи минимально необходимое исправление.

### 2.4. Изображения и анимации

Проверь:

- загрузку изображений и анимаций;
- размеры передаваемых ресурсов;
- ненужную предварительную загрузку;
- кеширование;
- влияние медиа на основной поток;
- производительность списков упражнений;
- повторную загрузку ресурсов при навигации.

**Важно:** существующие HD-анимации и работа по #986 должны быть сохранены.

Не заменяй качественные анимации низкокачественными, не сокращай их длительность и не отключай движение ради улучшения синтетических показателей.

Не изменяй визуальную стилистику YFC.

### 2.5. Landing и Core Web Vitals

Проверь реальные публичные страницы и Landing.

Измерь, где технически возможно:

- LCP;
- CLS;
- INP;
- объём начальной загрузки;
- блокирующие ресурсы;
- загрузку шрифтов;
- влияние hero-анимации;
- кеширование;
- мобильную и десктопную производительность.

Разделяй лабораторные измерения и реальные пользовательские данные.

Если CrUX, RUM или данные физических устройств недоступны, укажи `NO_DATA`. Не придумывай результаты.

## 3. Реализация улучшений

После диагностики:

1. Составь перечень подтверждённых проблем.
2. Оцени влияние каждой на пользователя.
3. Отсортируй исправления по пользе и сложности.
4. Реализуй наиболее значимые улучшения.
5. Сохрани исходные сценарии и контракты приложения.
6. Не проводи широкий рефакторинг без измеримой пользы.

Предпочтительные подходы:

- оптимизация существующих компонентов;
- точечное разделение больших чанков;
- устранение лишних запросов;
- оптимизация тяжёлых вычислений;
- исправление неэффективного кеширования;
- уменьшение количества ненужных операций браузера.

Не внедряй новую архитектуру, новый маршрутизатор или дополнительный глобальный менеджер состояния.

Не меняй backend, если производительность frontend можно улучшить без него. Если найден реальный backend-блокер, зафиксируй его для #817.

## 7. GitHub и подготовка релиза

Работай через обычный процесс репозитория:

1. Создай отдельную рабочую ветку от актуального `master`.
2. Выполняй изменения небольшими осмысленными коммитами.
3. Сохраняй чистую историю изменений.
4. Создай PR, связанный с #818.
5. Приложи результаты BEFORE/AFTER.
6. Добавь описание исправлений и тестовые доказательства.
7. Проверь обязательный CI на точном HEAD.
8. Проверь отсутствие конфликтов с актуальным `master`.
9. Исправь обнаруженные регрессии и повтори проверки.

Не создавай несколько конкурирующих PR для одного и того же исправления.

Если часть работы зависит от отдельного owner-gate, доведи независимые изменения до конца и явно отдели заблокированную часть.

**Не выполняй merge и production deploy без отдельного разрешения владельца.**
